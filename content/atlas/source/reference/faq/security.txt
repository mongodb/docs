How does |service| encrypt my data?
-----------------------------------

|service| protects customer data in transit with |tls|. |tls| is
enabled by default and cannot be disabled; it encrypts data sent to
|service| and data transmitted between nodes of an |service| cluster.
|service| also encrypts customer data at rest. Encryption at rest is
always enabled using Advanced Encryption Standard (AES)-256.

- **{+atlas-core-full+}:** On an :ref:`{+atlas-core-full+}
  <atlas-core-edition>` cluster, your cloud provider automates this disk
  encryption and manages the encryption keys. You can optionally enable
  :ref:`database-level encryption <atlas-core-encryption-at-rest>` using
  the WiredTiger Encrypted Storage Engine and bring your own key through
  :ref:`AWS KMS <security-aws-kms>`, :ref:`Google Cloud KMS
  <security-gcp-kms>`, or :ref:`Azure Key Vault <security-azure-kms>`.

- **{+atlas-infinite-full+}:** :ref:`{+atlas-infinite-full+}
  <atlas-infinite-edition>` is currently in :ref:`public preview
  <atlas-infinite-availability>`. In {+atlas-infinite-full+}, compute
  and storage are separate layers. {+atlas-infinite-full+} always
  encrypts customer data at the database level, before it leaves the
  compute layer and reaches the storage layer, which is shared across
  multiple customers. This storage layer does not have the encryption
  keys and cannot decrypt customer data. In public preview,
  customer-managed keys are available through :ref:`AWS KMS
  <security-aws-kms>`.

For more detail on encryption and |service| security controls, see
`Technical and Organizational Security Measures
<https://www.mongodb.com/legal/customer-service-agreement/technical-and-organizational-security-measures/>`__.

.. _infinite-faq-security:

How does {+atlas-infinite-full+} keep each customer's data separate from other customers?
--------------------------------------------------------------------------------

MongoDB {+atlas-infinite-cluster+}s are deployed in a dedicated VPC
that fully isolates customer data at the compute layer.
{+atlas-infinite-full+} keeps each tenant's data separate in the
storage layer in two ways:

- Every request your cluster makes to the storage layer is checked
  against your cluster's identity, so only your data is returned.

- {+atlas-infinite-full+} encrypts data before it reaches the storage
  layer. By default, MongoDB :ref:`manages a unique encryption key
  <atlas-infinite-encryption-at-rest>` for each |service| organization
  and rotates it automatically every 90 days. :ref:`Customer-managed
  keys <security-kms-encryption>` add another encryption layer, and you
  can migrate between default and customer-managed encryption in either
  direction.

Where can my data be processed or stored in {+atlas-infinite-full+}, and can I restrict this by region, jurisdiction, or cloud?
----------------------------------------------------------------------------------------------------------------------

Consistent with {+atlas-core-full+}, your application data in
{+atlas-infinite-full+} is only processed in the region(s) in which the
cluster is located. |service| gives you the ability to choose which
cloud provider and the specific region(s) a cluster is located in.

What review and analysis has been done to confirm the system is secure?
-----------------------------------------------------------------------

|service| undergoes regular reviews from both internal and external
security teams. The |service| production environment is subject to an
external penetration test by an industry recognized security firm at
least once per calendar year. Internally, |service| undergoes periodic
risk assessments, including technical vulnerability discovery and
analysis of business risks and concerns. Further, MongoDB conducts
regular scans of the underlying systems on which |service| is deployed
and of third-party code integrated into its products. For more details
refer `Technical
and Organizational Security Measures
<https://www.mongodb.com/legal/customer-service-agreement/technical-and-organizational-security-measures/>`__.

Can I disable TLS on my deployment?
-----------------------------------

No.

What versions of TLS does |service| support?
-------------------------------------------- 

|service| requires |tls| connections for all |service| clusters.
|service| supports |tls| protocol versions 1.2 and 1.3.

and the
`National Institute of Standards and Technology (NIST)
<https://www.nist.gov/news-events/news/2014/04/nist-revises-guide-use-transport-layer-security-tls-networks>`_.

If you have questions about |tls| support or cannot update your
applications to support |tls| 1.3, please contact |service|

How do I know if my applications support TLS 1.3?
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Applications whose underlying programming languages or security 
libraries predate |tls| 1.3 may require updating to a more recent 
version to support |tls| 1.3. You may also need to update the 
application host operating system to support |tls| 1.3.

MongoDB and |service| don't provide services to audit external
applications for which versions of |tls| support they support.
Third party services, such as
`howsmyssl.com <https://www.howsmyssl.com/s/api.html>`_
may provide the appropriate tooling. MongoDB doesn't endorse this
service, and its reference is only informational. Use your
organization's procedures for selecting the vendor or service for auditing
your applications.

What do I have to do to update my clusters for TLS 1.3?
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

- Conduct an audit of your applications for support of |tls| 1.3.
- Update all components of your technology stack that don't support
  |tls| 1.3.
- :ref:`Modify <scale-cluster-more-configuration-options>` your cluster
  configuration to use |tls| 1.3.
- If you have a :ref:`custom TLS 1.2 cipher configuration 
  <set-custom-cipher-suite-configuration>`, you must update 
  the configuration to include the |tls| 1.3 ciphers.

.. _faq-tls-ca:

Which certificate authority signs MongoDB Atlas TLS certificates?
-----------------------------------------------------------------

|service| cluster nodes' TLS certificates are signed by either Google Trust Services or
Let's Encrypt to improve high availability. Atlas uses both certificate authorities concurrently.
You must add CA certificates for the :guilabel:`GTS Root R1`, :guilabel:`GTS Root R2`,
:guilabel:`GTS Root R3`, and :guilabel:`GTS Root R4` root |certauth| from Google Trust Services
to your clients' trusted certificate stores, in addition to the ISRG Root X1 root |certauth|
from Let's Encrypt to ensure seamless service continuity.

|service| uses the :guilabel:`GTS Root R3` and :guilabel:`GTS Root R4` root CA certificates
for TLS 1.3 support.

.. note:: 
   
   Most application environments already have Let's Encrypt and Google Trust
   Services in their trusted |certauth| list.

To download the |certauth| certificates, see the
`Google Trust Services repository <https://pki.goog/repository/>`__ and 
`ISRG Root X1 <https://letsencrypt.org/certificates/>`__.

.. note:: 

   |service| automatically rotates the certificates. You don't need to
   run the :dbcommand:`rotateCertificates` command. Use the
   ``rotateCertificates`` command only if you want to rotate the
   certificates manually.

How often does an Atlas Cluster rotate TLS certificates?
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

|tls| certificates are valid for 90 days from the day it is issued.
Certificates are rotated 42 days before the certificate's expiration
date.

Use the following command to check expiration of your |tls| certificate
of a node:

.. code-block::

   echo | openssl s_client -showcerts -connect $HOSTNAME:$PORT 2> /dev/null | openssl x509 -noout -enddate

.. _tls-change-hard-code:

Hard-coded Certificate Authority
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

We don't recommend hard-coding or pinning `intermediate certificates
<https://letsencrypt.org/certificates/#intermediate-certificates>`__
because it introduces an operational burden and availability risk. If
Let's Encrypt or Google Trust Services rotates or replaces your pinned
intermediate certificate, your application might fail to connect, which
results in an outage.

If you must pin a certificate, pin it to |certauth| certificates and not
to any intermediate certificates.

Java Users
~~~~~~~~~~

Let's Encrypt's ISRG root certificate and Google Trust Services root
certificates are both available in the default trust store of `Java
version 7 after the 7u391 update
<https://www.oracle.com/java/technologies/javase/7-support-relnotes.html#JDK-8307134>`__
and `Java version 8 after the 8u381 update
<https://www.oracle.com/java/technologies/javase/8u381-relnotes.html#JDK-8307134>`__.
Use a Java release after 18 July 2023.

Ensure your Java client software is up-to-date. Use the latest Java
versions to leverage improvements beyond these new |certauth|
requirements for our |tls| certificates.

If you have your own trust store, add the Let's Encrypt and Google Trust
Services certificates to it. To learn more, see
:ref:`faq-tls-ca`

Windows Server Users
~~~~~~~~~~~~~~~~~~~~

The ISRG Root X1, GTS Root R1 and GTS Root R2 root |certauth| aren't
included by default in Windows Server, but it is available in the
`Microsoft Trusted Root Program
<https://docs.microsoft.com/en-us/security/trusted-root/participants-list>`__.


To configure Windows Server to download trusted root certificates, see
`Windows Documentation
<https://docs.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2012-r2-and-2012/dn265983(v=ws.11)>`__.

Amazon Linux AMI Users
~~~~~~~~~~~~~~~~~~~~~~

Some versions of `Amazon Linux AMI
<https://aws.amazon.com/amazon-linux-ami/>`__  may not have both ISRG
Root X1 and GTS Root R1 and R2 certificates. Please migrate to a newer
version of Amazon Linux for required root certificates. After June 2025,
we will require the support of ISRG Root X1, GTS Root R1 and R2
certificates for |service| to avoid certificate compatibility issues.

If you must use an older Amazon Linux AMI, manually install the ISRG
Root X1, GTS Root R1 and R2 root |certauth|.

Everyone Else
~~~~~~~~~~~~~

This change shouldn't impact you if you use a recent programming
language and operating system version.

Why did my TLS configuration change fail with an ``UNSAFE_TLS_TRANSITION error?``
--------------------------------------------------------------------------------------------------------

|service| prevents TLS configuration changes that could break 
communication between cluster nodes during a rolling update.

When you update TLS settings, |service| applies the changes one node at 
a time. During this process, nodes running the old configuration must 
still be able to connect to nodes running the new configuration. If 
your proposed changes remove all shared TLS versions or cipher suites, 
the nodes can't communicate, which leads to a partitioned cluster and 
potential downtime.

To protect cluster availability, |service| blocks these unsafe 
transitions and returns the ``UNSAFE_TLS_TRANSITION`` error.

``UNSAFE_TLS_TRANSITION`` Error Causes
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

This error typically occurs in the following scenarios when there is no 
overlap between the current and proposed TLS configurations:

- TLS version mismatch.

  - Example: Switching directly from TLS 1.2-only to TLS 1.3-only.

  - Result: Nodes using TLS 1.2 cannot connect to nodes requiring TLS 
    1.3.

- Cipher suite mismatch.

  - Example: Replacing all existing cipher suites with a completely 
    different set.

  - Result: Nodes have no shared cipher to negotiate a connection

``UNSAFE_TLS_TRANSITION`` Error Solution
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Make your TLS changes in phases, and ensure overlap between old and new 
settings:

For TLS versions:

1. Enable both TLS 1.2 and TLS 1.3.

#. Apply the change and allow the update to complete.

#. Remove TLS 1.2 in a follow-up update (if desired).

For cipher suites:

- Ensure at least one cipher suite is shared between the current and 
  new configurations during the transition.

``UNSAFE_TLS_TRANSITION`` Error Key Takeaway
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Avoid "all-at-once" TLS changes. Always maintain temporary
compatibility between old and new configurations to ensure a safe
rolling update.

What is |service|'s support policy for community and unsupported drivers?
-------------------------------------------------------------------------

|service| provides different levels of support for officially
supported drivers, community drivers, and unsupported configurations.

Driver Categories
~~~~~~~~~~~~~~~~~

**Officially Supported Drivers**

MongoDB develops and maintains these drivers, which are listed on
:driver:`mongodb.com/docs/drivers </>`. MongoDB's test matrix,
release process, and support SLA cover these drivers.

Officially supported drivers include :driver:`C </c/>`, :driver:`C++
</cxx/>`, :driver:`C# </csharp/>`, :driver:`Go </go/>`,
:driver:`Java </java-drivers/>`, :driver:`Kotlin </kotlin/>`,
:driver:`Node.js </node/>`, :driver:`PHP </php-drivers/>`,
:driver:`Python </python-drivers/>`, :driver:`Ruby </ruby-drivers/>`,
:driver:`Rust </rust/>`, :driver:`Scala </scala/>`, and :driver:`Swift
</swift/>`.

**Community Drivers**

Third-party developers create and maintain these drivers, which
implement MongoDB's published specifications or wire protocol.
Examples include Zookzook (Elixir), Mango (Dart), mongolite (R), and
mgo (Go).

**Unsupported Configurations**

Any officially supported or community driver used at an end-of-life
version.

Support Levels
~~~~~~~~~~~~~~

**Officially Supported Drivers (Current Version)**

The |service| SLA covers these drivers. MongoDB provides standard
troubleshooting and resolution, including investigation and fixes for
connection issues.

**Officially Supported Drivers (EOL Version)**

MongoDB provides best-effort support. MongoDB investigates issues but
might recommend upgrading to a current version.

**Community Drivers**

MongoDB provides best-effort, diagnosis-only support. Support helps
you determine whether an issue originates from the platform or the
driver. For driver-side issues, MongoDB provides available guidance
and refers you to the driver maintainer. MongoDB does not debug or
patch community driver code.

Responsibilities
~~~~~~~~~~~~~~~~

**What |service| Does**

|service| performs risk assessments for platform changes that affect
the connection layer, including TLS version changes, certificate
rotations, and authentication mechanism updates. |service| assesses
known fragility patterns even when the fragility originates in
client-side code.

For high-risk platform changes, |service| publishes guidance in
:ref:`release notes <atlas-release-notes>` and pre-maintenance notifications when
feasible.

**What |service| Does Not Do**

|service| does not:

- Test, certify, or guarantee the correctness of community drivers
- Test all community drivers in all configurations
- Commit to patching, reviewing, or maintaining community drivers

Community drivers must correctly implement TLS negotiation,
authentication, wire protocol, and failover behavior. Any
contributions MongoDB makes to community drivers are voluntary, not
contractual obligations.

SLA Coverage
~~~~~~~~~~~~

The |service| SLA covers officially supported MongoDB drivers at
current versions only. Outages caused by community driver bugs or
unsupported driver configurations fall outside the SLA.

Use :driver:`officially supported drivers </>` at current versions for
full SLA coverage and the best support experience.
