=====================================
MongoDB {+service+} Database Editions
=====================================

.. default-domain:: mongodb

.. facet::
   :name: genre
   :values: reference

.. meta::
   :keywords: database editions, atlas core, atlas infinite, compare editions
   :description: MongoDB Atlas offers two database editions. Atlas Core couples compute and storage on each node. Atlas Infinite separates compute and storage into independent layers. Compare scaling, recovery, and availability.

.. contents:: On this page
   :local:
   :backlinks: none
   :depth: 1
   :class: singlecol

|service| offers two database editions. Both editions run MongoDB and
use the same interface, drivers, APIs, and most operational workflows.
They differ in how they provision compute and storage:

- :ref:`{+atlas-core-full+} <atlas-core-edition>`: the |service|
  cluster architecture where compute and storage run on the same node.
  It is available across {+Free-clusters+}, {+Flex-clusters+}, and
  dedicated cluster tiers.
- :ref:`{+atlas-infinite-full+} <atlas-infinite-edition>`: an
  architecture that separates compute from storage into independent
  layers, designed for mission-critical high-performance use cases.
  {+atlas-infinite-full+} is available as a public preview, and both
  the product and its documentation might change during the preview
  period.

Compare Editions
----------------

.. list-table::
   :header-rows: 1
   :widths: 20 40 40

   * - Aspect
     - {+atlas-core-full+}
     - {+atlas-infinite-full+}

   * - Architecture
     - Compute and storage run on the same node. Each data-bearing
       node runs on a virtual machine with attached storage.
     - Compute and storage run as independent layers. MongoDB manages
       the storage layer separately from the compute nodes.

   * - Compute scaling
     - You change compute capacity by selecting a different cluster
       tier. {+service+} restarts the cluster's nodes when you change
       the tier, with no downtime on dedicated clusters.
     - You scale the cluster tier independently of storage. Scaling
       doesn't move your data, so it is fast.

   * - Storage scaling
     - You scale storage capacity and Input/Output Operations Per Second (IOPS) independently of compute on
       dedicated clusters, up to the maximum for the cluster tier. To
       add capacity beyond that maximum, you scale to a higher tier.
     - Storage capacity increases automatically based on usage,
       independently of the cluster tier, without downtime.

   * - Horizontal scaling
     - You shard a cluster when its data approaches the storage
       capacity, and add workload-specific nodes, such as read-only or
       analytics nodes, as needed.
     - Each highly available shard (HA shard), a unit distinct from a
       MongoDB :term:`shard`, stores up to 128 TB of logical data
       without requiring sharding. Adding workload-specific nodes is
       much faster.

   * - Recovery
     - {+service+} monitors your database regularly, and performs auto-healing
       if it discovers an issue. If it replaces a node, the new node performs
       an initial sync before it serves queries.
     - {+service+} monitors your database regularly, and performs auto-healing
       if it discovers an issue. If it replaces a node, the new node immediately
       connects to the storage layer, with no need for an initial sync.

   * - Cloud provider and tier availability
     - {+Free-clusters+}, {+Flex-clusters+}, and dedicated cluster
       tiers, on AWS, Azure, and Google Cloud.
     - Public preview: ``M10`` through ``M60`` replica sets in
       supported AWS regions, with storage capacity up to 128 TB per
       replica set.

   * - Feature coverage
     - Supports the full |service| feature set.
     - Some |service| features aren't :ref:`supported during public
       preview <atlas-infinite-availability>`.

Choose an Edition
-----------------

Consider :ref:`{+atlas-core-full+} <atlas-core-edition>` when:

- You want the full |service| feature set
- You need multi-region or multi-cloud clusters
- You need sharded clusters

Consider :ref:`{+atlas-infinite-full+}
<atlas-infinite-edition>` when:

- You want to scale compute and storage independently
- Your workload has spikes that are difficult to preprovision for
- You want to grow storage capacity without scaling the cluster tier
- You want faster failover and recovery

Confirm that your workload fits the :ref:`public preview
limitations <atlas-infinite-availability>` first.

The :ref:`{+atlas-infinite-full+} architecture
<atlas-infinite-architecture>` describes how the compute and storage
layers interact.
