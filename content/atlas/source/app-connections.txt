==============================
Atlas App Connections Overview
==============================

.. default-domain:: mongodb

.. facet::
   :name: genre
   :values: reference

.. meta::
   :keywords: app connections, oauth, delegated access, mcp, ai clients, partner applications, mongodb applications
   :description: Atlas App Connections is the MongoDB Atlas OAuth 2.1 platform that lets AI clients, partner applications, and MongoDB applications act on behalf of Atlas users through secure, user-delegated access.

.. contents:: On this page
   :local:
   :backlinks: none
   :depth: 2
   :class: singlecol

Atlas App Connections is the |service-fullname| OAuth 2.1 platform
that lets apps act on behalf of |service| users through user-delegated
access. When a user authorizes an app, the app receives tokens it can
use to call the {+atlas-admin-api+} with the same permissions the user
holds in their |service| organizations.

This page explains the concepts that underlie user-delegated access
through Atlas App Connections. These concepts apply to every type of
app. The governance and revocation controls this page describes,
such as organization-level access modes and token lifetime, are
specific to AI clients; partner applications and |compass| have
their own governance controls, linked from their respective
subsections below. To connect or manage a specific type of app, see
the documentation for that app type.

.. _app-types:

App Types
---------

AI Clients
~~~~~~~~~~

AI clients reach |service| through the MongoDB MCP Server and act on
a user's behalf through the tools that the MCP Server exposes. An
Organization Owner controls whether AI clients can connect to an
organization and which access mode they use.

To compare the ways an AI client can connect, see
:ref:`remote-mcp-access-models`. To enable or restrict AI client
access for your organization, see
:ref:`remote-mcp-manage-ai-client-access`.

Partner Applications
~~~~~~~~~~~~~~~~~~~~

Partner applications are third-party applications that integrate with
|service| directly through the OAuth 2.1 Authorization Code flow with
Proof Key for Code Exchange (PKCE). A partner application obtains its
own access and refresh tokens and calls the {+atlas-admin-api+} with
the authorizing user's permissions, without the MCP Server in
between.

To integrate your application with |service| as a partner, see
:ref:`partner-integration-guide`. If your integration needs to
receive rotated database credentials automatically, see
:ref:`partner-credential-rotation`.

First-Party Applications
~~~~~~~~~~~~~~~~~~~~~~~~

Atlas App Connections in Compass lets a user sign in with Atlas and
securely let Compass use their existing Atlas permissions to provide
a smoother Atlas-connected experience.

Compass delegated access is enabled by default. You cannot disable
this feature in Atlas. To disable Atlas App Connections in Compass,
open your :ref:`Compass config file <config-file>` and toggle
``enableAtlasSignIn`` to ``off``.

The authentication token has the same permissions as the Atlas user.
Compass stores the encrypted refresh tokens on the Atlas user's
disk. The default refresh token settings are a 7-day inactivity
window and a 30-day maximum lifetime. These tokens remain until they
expire or a user revokes them, which matters when employees depart
or hand off devices. You can also lower the refresh token's maximum
lifetime in your organization's settings. For instructions on how
to remove a user, see :ref:`atlas-org-users`.

How Delegated Access Works
--------------------------

When a user authorizes an app, the app acts on behalf of that
user, not as a separate entity. The app receives tokens that let it call the
{+atlas-admin-api+} with the **same permissions the user holds** in
their |service| organizations and projects. If the user cannot
perform an action, the app cannot perform it on their behalf
either. The app never receives the user's password or long-lived
credentials.

For AI clients specifically, effective access is the more
restrictive of two factors: the authorizing user's existing
|service| permissions, and the read-only or read-write access mode
that an Organization Owner configures for the organization. The
access mode can reduce what an AI client can do, but never grants
more access than the user's own permissions allow.

Because access is inherited from the user's own permissions:

- The app's effective permissions change automatically when the
  user's roles change.
- Operations against an organization succeed only when that organization
  allows AI client connections *and* the authorizing user holds the
  required role for the operation.

Users always delegate all of their access when they authorize a
client, which can be more than the client needs for a given task.
To limit delegations to their organization, Organization Owners can
take the following actions:

- |service| disables AI client access by default for existing
  organizations and for new organizations an existing |service|
  user creates.
- Organization Owners can enable AI client access for only the
  organizations that need it.
- Organization Owners can specify a read-only or read-write access
  mode for AI clients.

To learn more, see :ref:`remote-mcp-access-models`.

Authorization and Consent
-------------------------

Apps obtain delegated access through the OAuth 2.1 Authorization
Code flow with Proof Key for Code Exchange (PKCE). The PKCE flow is
as follows:

.. procedure::
   :style: normal

   .. step:: The user starts the connection from the app, not from
      Atlas.

      The exact steps to start a connection vary by app. For AI
      clients, see the MongoDB MCP Server documentation for
      client-specific setup guidance.

      The app controls how it directs the user to the authorization
      page, such as through a new browser window, a pop-up, or a
      redirect within the existing window.

   .. step:: Atlas prompts the user to sign in, if they are not
      already.

      A user who does not yet have an Atlas account can create one
      during this step and then continues the connection flow.

   .. step:: Atlas shows a consent screen listing the permissions
      being requested.

      The user selects **Authorize** to grant access or **Decline**
      to cancel.

   .. step:: Atlas redirects the user back to
      the app.

      The connection is now active.

To learn more,
see :ref:`remote-mcp-security`.

Organization-Level Governance
-----------------------------

|service| disables AI client connections by default for existing
organizations and for new organizations existing |service| users create.
An Organization Owner must explicitly enable AI client
access before an AI client can use delegated access against that
organization. |service| enables AI client access by default for an
organization that a brand new user creates during sign-up, when the
user doesn't have an existing Atlas account.

Organization Owners can:

- Enable or disable AI client access for the organization.
- Choose a read-only or read-write access mode.
- Set the maximum token lifetime for authorized connections.

The access mode you configure and the authorizing user's own
|service| permissions together determine what an AI client can do.
An AI client's effective access is always the more restrictive of
the two.

For setup and configuration steps, see
:ref:`remote-mcp-manage-ai-client-access`.

Access Revocation and Timing
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

When a user authorizes delegated access to an app, the app receives
an access token and a refresh token. The app presents its access token with
each {+atlas-admin-api+} call. When the access token expires, the
app uses its refresh token to obtain a new access token without
requiring the user to sign in again.

The time it takes for an AI clients access revocation to take effect differs depending on
who revokes access:

- **An Organization Owner disables AI client access for the
  organization:** control-plane access is revoked immediately for
  every AI client connected to the organization.
- **A user revokes an individual AI client's access:** changes may
  take up to 10 minutes to take effect.

.. warning:: Deprovision federated users promptly

   When your organization uses `Role Mapping
   <https://www.mongodb.com/docs/atlas/security/manage-role-mapping/>`__
   to manage Atlas user access through Identity Provider groups, a
   federated user's permissions in Atlas only update when that user
   logs in. This is known as Just-In-Time (JIT) Provisioning. If
   your organization doesn't deprovision a user through the
   {+atlas-admin-api+} when that user loses access, an AI client
   that holds a refresh token for that user can continue to act on
   their behalf.

   To limit this risk:

   - Deprovision users through the {+atlas-admin-api+} as soon as
     they lose access.
   - Set the maximum refresh token lifetime for your organization to
     reduce how long a client can retain access after a user is
     deprovisioned.

   To learn more, see :ref:`AI Client Access Lifetime
   <remote-mcp-manage-ai-client-access-lifetime>`.

Connect and Manage Apps
-----------------------

The following guidance applies to every type of app that connects
through Atlas App Connections, whatever your role.

Manage App Access
~~~~~~~~~~~~~~~~~

Organization Owners control whether apps can connect to their
organization at all. From :guilabel:`Organization Settings` >
:guilabel:`App Connections`, an Organization Owner can enable or
disable third-party app connections, set the maximum refresh token
lifetime for authorized apps, and review which apps users in the
organization have authorized.

Connect an App to Your Account
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Individual users authorize the apps that act on their behalf. When
you connect an app, |service| shows you a consent screen listing the
access the app requests. You can review the apps you have connected
at any time and revoke any of them, which stops the app from acting
on your behalf.

.. _atlas-app-connections-known-limitations:

Limitations
-----------

When planning your integration, consider the following scope and
boundaries of Atlas App Connections:

- Organization Owners cannot revoke individual access granted from a
  user to a client. To remove access delegated by any user in an
  organization, disable AI client access for the entire
  organization. Enabling AI client access for an organization
  enables all current and future AI clients that support delegated
  access.
- {+atlas-admin-api+} IP access lists do not apply to delegated-access
  traffic. An AI client's delegated-access calls can't be blocked
  based on the IP address the AI client connects from.
- Revocation does not remove security artifacts that the client
  created during its authorized access. These artifacts remain valid
  independent of the client's revoked tokens:

  - Service accounts and API keys are control-plane artifacts. Audit
    them, then remove or rotate them to end the client's
    control-plane access. To learn more, see
    :ref:`rotate-service-account-secrets`.
  - Database users are data-plane artifacts. Review them alongside
    the other database identities in your project. To learn more, see
    :ref:`mongodb-users`.
