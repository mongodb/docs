You can integrate MongoDB with `Mastra <https://mastra.ai/>`__ to store
and search vector embeddings for your AI applications.
Mastra is an open-source TypeScript agent framework that 
provides primitives for building AI applications, including workflows,
RAG, and evals.

To learn more, see the `Mastra documentation <https://mastra.ai/en/docs>`__ or the
:github:`Mastra GitHub repository <mastra-ai/mastra>`.

.. _mastra-overview:

Overview
--------

You can use MongoDB as a vector store in Mastra. By combining
{+avs+} with the Mastra ``MongoDBVector`` class, you can implement
the following capabilities:

- Store and retrieve vector embeddings using MongoDB as your vector database
- Filter your vector search results using MongoDB query syntax
- Rerank your search results
- Run a hybrid search that combines semantic and full-text search

To use MongoDB with Mastra agents, including agentic RAG, agent memory,
and workspace search, see :ref:`mastra-agents`.

.. _mastra-vector-store:

Vector Store Configuration
--------------------------

MongoDB is a `supported database <https://mastra.ai/en/docs/rag/vector-databases#supported-databases>`__ in Mastra.
The ``MongoDBVector`` class allows you to store and retrieve vector embeddings 
from MongoDB. You can use this component to implement |rag| by storing 
embeddings from your data and retrieving them using {+avs+}.

This component requires that you create an :ref:`{+avs+} Index <avs-types-vector-search>`.

To use the MongoDB vector store with Mastra, import the ``MongoDBVector`` class,
create an object with the class, and specify your MongoDB connection details.
For example:

.. literalinclude:: /includes/ai-integrations/mastra/instantiate-vector-store.ts
   :language: typescript

The examples in the following sections use this ``MongoDBVector`` instance.

Methods
-------

This section highlights 
the most relevant methods for working with MongoDB as a vector store.
For a full list of methods, see the `Mastra documentation 
<https://mastra.ai/en/reference/vectors/mongodb>`__. 

MongoDB supports the following embedding modes:

- **Automated Embedding**: MongoDB uses a |voyage| model to automatically
  generate vector embeddings for your text data and your query string.
  To learn more, see :ref:`Automated Embedding <avs-auto-embeddings>` in the
  {+avs+} documentation.

- **Manual Embedding**: Generate the vector embeddings yourself by
  managing the embedding model, the index dimensions, and the embedding
  operation. To learn more, see :ref:`Create Vector Embeddings
  Manually <create-vector-embeddings>` in the {+avs+} documentation.

.. _mastra-existing-collection:

Existing Collection Indexes
---------------------------

You can create a {+avs+} index on an existing MongoDB collection,
instead of copying the data into a collection that Mastra manages.
To specify the collection, pass the ``collectionName`` parameter to
the ``createIndex()`` method. These examples require
``@mastra/mongodb`` version 1.28.0 or later.

.. note::

   A new index on an existing collection is read-only by default. The
   ``upsert()``, ``updateVector()``, ``deleteVector()``, and
   ``deleteVectors()`` methods generate an error instead of modifying
   your documents. To store embeddings, write them to your corresponding
   documents from your application, or use :ref:`Automated Embedding
   <avs-auto-embeddings>`.

.. tip:: Filter Fields

   The preceding example filters documents by the ``year`` field, which the
   :ref:`createIndex() example <mastra-existing-collection-idx>` declares
   in the ``filterFields`` parameter. If you filter on a field that you
   don't declare in ``filterFields``, or use an operator that
   ``$vectorSearch`` doesn't support, ``MongoDBVector`` filters the
   results in two steps. The vector store first runs a separate
   ``$match`` query and loads the matching ``_id`` values into memory.
   Then, the store passes those values to {+avs+}.

   These additional steps increase costs and latency, since the
   ``$match`` query runs a collection scan unless a regular MongoDB
   index covers the filtered fields. If more than 100,000 documents
   match the filter, the query throws a ``TOO_MANY_CANDIDATES``
   error.

Delete the Index
~~~~~~~~~~~~~~~~

To delete a {+avs+} index, call the ``deleteIndex()`` method and pass
the same ``indexName`` value that you passed to ``createIndex()``.
The method behavior differs depending on collection ownership:

- **Mastra collection**: This method deletes the entire collection that
  ``MongoDBVector`` created, including its documents. If another index
  uses the collection, the method throws an error and has no effect.
- **Existing MongoDB collection**: This method deletes only the {+avs+}
  and full-text indexes that ``MongoDBVector`` created. Your
  collection, documents, and other indexes remain.

The following example deletes the ``movies_index`` index:

register, the method throws an error and does not delete anything.

Configuration Options
~~~~~~~~~~~~~~~~~~~~~

When you create a reranker, you can set the following configuration
options:

.. list-table::
   :header-rows: 1

   * - Option
     - Description
   * - ``model``
     - **(Required)** The reranking model to use. To view the available
       models, see :ref:`voyage-rerankers` in the |voyage| documentation.
   * - ``apiKey``
     - Your API key. MongoDB model API keys work only with MongoDB
       endpoints, and Voyage AI API keys work only with Voyage AI
       endpoints. Defaults to the ``VOYAGE_API_KEY`` environment
       variable.
   * - ``baseUrl``
     - The endpoint for the Voyage API. Defaults to
       ``https://api.voyageai.com/v1``, the Voyage AI endpoint.
   * - ``truncation``
     - Whether to truncate inputs that exceed the model's context
       length. Defaults to ``true``.

.. _mastra-hybrid-search:

Hybrid Search
-------------

.. important::

   Hybrid search requires MongoDB 8.0 or later.

You can use the Mastra ``MongoDBVector`` class to run a
:ref:`hybrid search <as_hybrid-search>` on your data. Hybrid search
combines semantic search with {+avs+} and full-text search with
{+fts+} to help improve the relevance of your search results. When
your queries need both semantic matches and exact keyword matches,
such as product names or error codes, use hybrid search. The
``hybridQuery()`` method runs both searches and then merges the
results by using the :pipeline:`$rankFusion` stage.

To filter the results, pass a ``filter`` object that uses the same
syntax as :ref:`metadata filtering <mastra-metadata-filtering>`.
MongoDB applies the filter to both searches before it merges the
results, but each search applies the filter at a different point:

- {+avs+} filters documents before it searches. You can declare the
  fields that you filter on in the ``filterFields`` parameter when you
  create the index. If your filter uses only declared fields and
  `operators that {+avs+} supports
  <https://www.mongodb.com/docs/vector-search/query/aggregation-stages/vector-search-stage/#pre-filter-for-top-level-embeddings>`__,
  MongoDB applies it inside the search. Otherwise, if the filter
  matches more than 100,000 documents, the query fails.

- {+fts+} applies the filter after it searches. MongoDB applies the
  filter on the server, not in your application. A broad full-text
  query combined with a narrow filter can be slower.

Hybrid search requires an existing {+avs+} index that contains
documents. To create the index and store documents, see the
:ref:`createIndex() <mastra-create-index>` and
:ref:`upsert() <mastra-upsert>` sections. The ``createIndex()``
method also creates a full-text search index on all fields in your
collection. To index only specific fields, or to search an
:ref:`existing collection <mastra-existing-collection>`, use the
``createSearchIndex()`` method instead. To learn more, see
`createSearchIndex()
<https://mastra.ai/integrations/vectors/mongodb#createsearchindex>`__
in the Mastra documentation.

Before you run a hybrid search, use the `waitForSearchIndexReady()
<https://mastra.ai/integrations/vectors/mongodb#waitforsearchindexready>`__
method to wait for the full-text search index to be ready. Then,
complete the following steps.

.. procedure::
   :style: normal

   .. step:: Run a hybrid search query.

      Call the ``hybridQuery()`` method with two queries: a ``vector``
      object for the {+avs+} query and a ``text`` object for the
      full-text query. MongoDB ranks the results of each search, and
      then merges the two rankings into a fusion score. MongoDB returns
      this score in the ``score`` field of each result.

      Optionally, set the ``weights`` field to control how much each
      search counts toward the final order. By default, both searches
      count equally. To favor vector matches instead, give ``vector``
      the higher weight. Each weight must be a non-negative number,
      and at least one weight must be greater than ``0``. An omitted
      weight defaults to ``1``.

      The following examples search for
      ``space opera about isolation``. They count full-text matches
      twice as heavily as vector matches and return the top 5
      results.

      Select the :guilabel:`Automated Embedding` or
      :guilabel:`Manual Embedding` tab to view an example that uses
      your preferred embedding mode:

      .. tabs::

         .. tab:: Automated Embedding
            :tabid: hybrid-query-auto

            The following example passes your query text in
            ``vector.query``, and MongoDB generates the query vector.

            .. literalinclude:: /includes/ai-integrations/mastra/hybrid-search.ts
               :language: typescript
               :category: snippet
               :start-after: start-hybrid-query-auto
               :end-before: end-hybrid-query-auto

            The full-text query searches the ``document`` field, where
            MongoDB stores your text by using Automated Embedding.
            MongoDB sends both the text that you store and your query
            text to an embedding model to generate vectors. By default,
            the model runs on MongoDB infrastructure in any cloud
            provider and geography. To restrict where MongoDB processes
            your text, see `Configure the Inference Scope
            <https://www.mongodb.com/docs/vector-search/crud-embeddings/automated-embedding/management/?deployment-type=atlas#configure-the-inference-scope>`__.

         .. tab:: Manual Embedding
            :tabid: hybrid-query-manual

            The following example generates an embedding for your

   .. step:: (Optional) Add native reranking.

      .. important::

         Native reranking requires an |service| cluster that runs
         MongoDB 9.0 or later, with :guilabel:`Native Reranking`
         enabled in your project settings. Reranking sends your query
         and the text in the ``rerank.paths`` fields to a |voyage|
         reranking model, which runs outside your cluster. By
         default, MongoDB uses the ``rerank-2.5`` model. To use a
         different model, set the ``rerank.model`` field. To learn
         about the requirements for each model, see
         :ref:`rerank-requirements`.

      You can refine the order of your hybrid search results by adding
      a ``rerank`` object to your query. MongoDB passes the merged
      results to a reranking model, which scores each document by its
      relevance to your query and reorders the results. Because the
      reranker sets the final order, the ``weights`` field affects only
      which documents MongoDB reranks.

      With native reranking, MongoDB calls the reranking model as part
      of your hybrid search query. If your cluster doesn't meet the
      requirements for native reranking, you can call a reranking model
      from your application instead. To learn more, see
      :ref:`mastra-reranking`.

      When you enable reranking, the ``score`` field of each result
      contains the reranking score instead of the fusion score. The
      two scores use different scales.
