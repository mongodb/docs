==============================================================
Install |text-search| and |vector-search| on multiple Clusters
==============================================================

.. facet::
   :name: genre
   :values: tutorial

.. meta::
   :keywords: vector search, mongodb search, mongot, multi-cluster,
      kubernetes, install, replica set, sharded cluster, external
   :description: Deploy MongoDB Search and Vector Search across many Kubernetes clusters with the MongoDB Controllers for Kubernetes Operator against an external MongoDB deployment.

.. default-domain:: mongodb

.. contents:: On this page
   :local:
   :backlinks: none
   :depth: 2
   :class: singlecol

You can use the |k8s-op-short| to deploy |text-search| and
|vector-search| across multiple |k8s| clusters for an external
MongoDB deployment. In this case the |k8s-op-short| just manages 
``mongot``, not the external MongoDB deployment. Your MongoDB 
deployment is external to the |k8s-op-short|. It can run: 

- Outside |k8s|, such as on virtual machines
- In |k8s| clusters, but not managed by the |k8s-op-short|

The |k8s-op-short| runs in a single, central cluster and deploys 
a ``mongot`` group into each |k8s| cluster that you list in the
``spec.clusters`` field of the ``MongoDBSearch`` custom resource.
Each ``mongot`` group syncs only from the MongoDB members that you
map to it. You control this mapping with member tags, which you set 
later in this procedure.

Select your configuration to filter the installation procedure
for your deployment.

.. note::

   Multi-cluster deployments require MongoDB Enterprise Edition and
   an external MongoDB deployment. Multi-cluster deployments in which 
   the |k8s-op-short| manages the MongoDB deployment aren't currently 
   supported as source to the multi-cluster Search deployment. See the
   :ref:`Supported Topologies <k8s-fts-vs-supported-topologies>`.

   Overview
   --------

   .. selected-content::
      :selections: external, repl

      The ``MongoDBSearch`` resource uses ``spec.source.external``
      to connect to your existing external replica set. Each
      ``mongot`` group syncs from a specific subset of your replica
      set members. To map each ``mongot`` group to the members it
      should sync from, you tag your replica set members and set
      ``syncSourceSelector.matchTagSets`` on each cluster entry, in
      ``MongoDBSearch`` resource, to match those tags. This mapping 
      ensures that each ``mongot`` group syncs only from its 
      intended members instead of arbitrary members.

      .. image:: /images/mongodb-k8s-multi-cluster-replicaset-search-arch.svg
         :width: 740px
         :alt: Architecture diagram showing the high-level architecture of a multi-cluster-Kubernetes
               deployment for an external replica set using the
               MongoDB Controllers for Kubernetes Operator.

   .. selected-content::
      :selections: external, shard

      The ``MongoDBSearch`` resource uses
      ``spec.source.external.shardedCluster`` to connect to your
      existing external sharded cluster. Each ``mongot`` group syncs
      from a specific shard of the MongoDB deployment. To map each
      ``mongot`` group to the members it should sync from, you tag
      your shard members and set ``syncSourceSelector.matchTagSets`` on
      each cluster entry, in the ``MongoDBSearch`` resource, to match
      those tags. This mapping ensures that each ``mongot`` group
      syncs only from its intended shard.

      Search queries for a shard must always target that shard's
      ``mongot`` group. The per-shard ``externalHostname`` that you
      set on each cluster entry and the managed Envoy load balancer
      that the |k8s-op-short| deploys enable this routing: Envoy uses
      |tls| |sni| to send each shard's traffic to the ``mongot``
      group for that shard, so search queries never cross shard
      boundaries.

      .. image:: /images/mongodb-k8s-multi-cluster-sharded-search-arch.svg
         :width: 740px
         :alt: Architecture diagram showing the high-level architecture of a multi-cluster-Kubernetes
               deployment for an external sharded cluster using the
               MongoDB Controllers for Kubernetes Operator.

   Prerequisites
   -------------

   .. selected-content::
      :selections: external, repl

      Before you deploy |text-search| and |vector-search| across
      many clusters for an external replica set, complete the
      following:

      - Deploy a MongoDB Enterprise Edition replica set running
        version 8.3.4 or later, externally to the |k8s-op-short|.
        The deployment must require |tls| connections, and every 
        replica set member must be reachable from each |k8s| 
        cluster where the |k8s-op-short| deploys ``mongot``.
      - Verify that your ``mongot`` and MongoDB Server versions are
        compatible. See
        :ref:`k8s-fts-vs-compatibility-requirements`.
      - Confirm that the |k8s| API server in each member cluster is
        reachable from the central cluster. The |k8s-op-short| must
        be able to create and reconcile ``mongot`` resources in all
        member clusters.

   .. selected-content::
      :selections: external, shard

      Before you deploy |text-search| and |vector-search| across
      many clusters for an external sharded cluster, complete the
      following:

      - Deploy a MongoDB Enterprise Edition sharded cluster running
        version 8.3.4 or later, externally to the |k8s-op-short|.
        The deployment must require |tls| connections, and every 
        |mongos| router and shard member must be reachable from each 
        |k8s| cluster where the |k8s-op-short| deploys ``mongot``.
      - Verify that your ``mongot`` and MongoDB Server versions are
        compatible. See
        :ref:`k8s-fts-vs-compatibility-requirements`.
      - Confirm that the |k8s| API server in each member cluster is
        reachable from the central cluster. The |k8s-op-short| must
        be able to create and reconcile ``mongot`` resources in all
        member clusters.

      .. important::

         Shard names must follow RFC 1123 DNS label rules, which
         allow lowercase alphanumeric characters or hyphens (``-``)
         and require starting with a letter and ending with an
         alphanumeric character. Underscores aren't allowed. The
         combined length of the resource name and shard name must be
         less than 50 characters.

            .. step:: Tag your external replica set members by cluster.

               Each ``mongot`` group syncs from a specific subset of
               your replica set members. To map each ``mongot`` group to
               the members it should sync from, you tag your replica set
               members and reference those tags in the
               ``syncSourceSelector.matchTagSets`` field of the
               ``MongoDBSearch`` resource.

               On your external replica set, add a member tag to each
               ``mongod`` member that identifies the ``mongot`` group
               that should sync from it. A member tag is a key-value
               pair in the member's replica set configuration, such as
               ``{ "vm-zone": "us-west-1" }``. Give every member that
               you want a given ``mongot`` group to sync from the same
               tag value, and use a distinct value for each ``mongot``
               group. To learn how to set member tags, see
               :ref:`replica set tag sets
               <replica-set-configuration-tag-sets>`.

               In a later step, you set ``syncSourceSelector.matchTagSets``
               on each ``spec.clusters`` entry to the tag value for that
               cluster's ``mongot`` group. The |k8s-op-short| passes the
               tag to ``mongot`` as a ``readPreferenceTags`` filter, so
               each ``mongot`` group syncs only from the replica set
               members that carry the matching tag. Record the tag value
               that you assign to each ``mongot`` group so that the
               ``matchTagSets`` values match exactly.

   Install |text-search| and |vector-search|
   ------------------------------------------

   Procedure
   ~~~~~~~~~

   .. selected-content::
      :selections: external, repl

      .. procedure::
         :style: normal

         .. step:: Create the search sync user Secret.

            Create a |k8s| Secret that stores the password for the
            ``search-sync-source`` user. The ``mongot`` process uses
            this credential to connect to your external replica set
            and build search indexes:

            .. code-block:: shell

               kubectl create secret generic \
                 "${MDB_SEARCH_RESOURCE_NAME}-search-sync-source-password" \
                 --from-literal=password="${MDB_SEARCH_SYNC_USER_PASSWORD}" \
                 -n "${MDB_NS}" \
                 --context "${K8S_CTX_0}"

         .. step:: Replicate Search Secrets to member clusters.

            The |k8s-op-short| doesn't automatically replicate
            Secrets with the ``Search`` prefix to member clusters.
            Copy the TLS certificates and sync password from the
            central cluster to each additional member cluster:

            .. literalinclude:: /includes/code-examples/search/12-search-rs-multi-cluster/code_snippets/12_0317_replicate_search_secrets.sh
               :language: shell
               :copyable: true
               :linenos:

         .. step:: Create and deploy the MongoDBSearch resource.

            Apply the ``MongoDBSearch`` custom resource. Configure
            the resource for your external multi-cluster replica set:

            - Set ``spec.source.external`` with the ``hostAndPorts``
              seed list, ``username``, and ``passwordSecretRef`` for
              your external replica set, and the CA under
              ``spec.source.external.tls.ca``.
            - Add one entry to ``spec.clusters`` per member cluster,
              each with a unique ``name`` and ``index``, the number of
              ``replicas`` (the number of ``mongot`` instances the
              |k8s-op-short| runs in that cluster), and
              ``syncSourceSelector.matchTagSets`` that match the cluster
              tags on your replica set members.
            - Set
              ``spec.clusters[].loadBalancer.managed.externalHostname``
              on each ``spec.clusters`` entry to a distinct hostname
              so that each member cluster's Envoy load balancer has
              its own hostname. For replica set sources, don't use
              the ``{shardName}`` placeholder. Because your
              MongoDB deployment is external, you must expose each
              operator-managed Envoy load balancer outside its
              cluster so that your MongoDB members can reach it, for
              example, through a |k8s| Service of type
              ``LoadBalancer`` or an OpenShift Route. Set each
              ``externalHostname`` to a hostname that resolves to
              that external endpoint. When you expose the Envoy load
              balancer externally, it's recommended to just expose the ``mongot-grpc`` (27028) port.

            .. note:: ``externalHostname`` Depends on Your MongoDB Deployment

               You set ``externalHostname`` because your MongoDB
               deployment isn't managed by the same |k8s-op-short|
               that manages ``mongot``. Its value must be an
               externally resolvable hostname that your ``mongod``
               members use to reach the Envoy load balancer. 

            The |k8s-op-short| reads each entry in ``spec.clusters``,
            creates a ``mongot`` StatefulSet in the corresponding

         .. step:: Configure search parameters on your external

            Point ``mongotHost`` and

            .. note:: ``mongotHost`` Depends on Your MongoDB Deployment

            Set ``searchTLSMode`` to ``requireTLS`` and

         .. step:: Create the search sync user Secret.

            Create a |k8s| Secret that stores the password for the
            ``search-sync-source`` user. The ``mongot`` process uses
            this credential to connect to your external sharded
            cluster and build search indexes:

            .. code-block:: shell

               kubectl create secret generic \
                 "${MDB_SEARCH_RESOURCE_NAME}-search-sync-source-password" \
                 --from-literal=password="${MDB_SEARCH_SYNC_USER_PASSWORD}" \
                 -n "${MDB_NS}" \
                 --context "${K8S_CTX_0}"

         .. step:: Tag your external shards by cluster.

            Each ``mongot`` group syncs from a specific shard. To map each ``mongot`` group to the
            members it should sync from, you tag your shards
            and reference those tags in
            ``syncSourceSelector.matchTagSets``.

            On your external sharded cluster, add a member tag to
            each shard's ``mongod`` members that identifies the
            ``mongot`` group that should sync from it. A member tag
            is a key-value pair in the member's replica set
            configuration, such as ``{ "vm-zone": "us-west-1" }``.
            Give every member that you want a given ``mongot`` group
            to sync from the same tag value, and use a distinct value
            for each ``mongot`` group. Apply the tags to the members
            of each shard independently. To learn how to set member
            tags, see :ref:`replica set tag sets
            <replica-set-configuration-tag-sets>`.

            In a later step, you set ``syncSourceSelector.matchTagSets``
            on each ``spec.clusters`` entry to the tag value for that
            cluster's ``mongot`` group. The |k8s-op-short| passes the
            tag to ``mongot`` as a ``readPreferenceTags`` filter, so
            each ``mongot`` group syncs only from the shard members
            that carry the matching tag. Record the tag value that
            you assign to each ``mongot`` group so that the
            ``matchTagSets`` values match exactly.

         .. step:: Replicate Search Secrets to member clusters.

            The |k8s-op-short| doesn't automatically replicate
            Secrets with the ``Search`` prefix to member clusters.
            Copy the per-(cluster, shard) TLS certificates, the LB
            certificates, and the sync password from the central
            cluster to each additional member cluster:

            .. literalinclude:: /includes/code-examples/search/13-search-sharded-multi-cluster/code_snippets/13_0317_replicate_search_secrets.sh
               :language: shell
               :copyable: true
               :linenos:

         .. step:: Create and deploy the MongoDBSearch resource.

            Apply the ``MongoDBSearch`` custom resource. Configure
            the resource for your external multi-cluster sharded
            cluster:

            - Set ``spec.source.external.shardedCluster`` with the
              ``router.hosts`` for your |mongos| routers and a
              ``shards`` entry for each shard that lists its
              ``shardName`` and member ``hosts``, and set the CA
              under ``spec.source.external.tls.ca``.
            - Add one entry to ``spec.clusters`` per member cluster,
              each with a unique ``name`` and ``index``, the number of
              ``replicas`` per shard, and
              ``syncSourceSelector.matchTagSets`` that match the cluster
              tags on your shard members.
            - Set
              ``spec.clusters[].loadBalancer.managed.externalHostname``
              on each ``spec.clusters`` entry to a distinct template
              that contains a ``{shardName}`` placeholder. The
              |k8s-op-short| expands this
              template per shard, and Envoy uses |tls| |sni| to route
              each shard's traffic to the ``mongot`` group for that
              shard. This is the endpoint that each shard's ``mongod``
              members use for ``mongotHost`` and
              ``searchIndexManagementHostAndPort``. Because your
              sharded cluster is external, you must expose each
              operator-managed Envoy load balancer outside its
              cluster so that your shard members can reach it, for
              example, through a |k8s| Service of type
              ``LoadBalancer`` or an OpenShift Route. Set each
              ``externalHostname`` to a hostname that resolves to
              that external endpoint. When you expose the Envoy load
              balancer externally, it's recommended to just expose the ``mongot-grpc`` (27028) port.

              You can set these parameters directly on each ``mongod``
              member or through the |com| UI. To use the |com| UI,
              follow the steps in
              :ref:`k8s-search-set-parameters-repl-multiple`, and set
              ``mongotHost`` and ``searchIndexManagementHostAndPort``.

            - Set
              ``spec.clusters[].loadBalancer.managed.routerHostname``
              to the shard-agnostic, cluster-level endpoint that your
              |mongos| routers use to reach that cluster's ``mongot``
              instances. Unlike ``externalHostname``, the
              |k8s-op-short| uses this value verbatim, so it must not
              contain a ``{shardName}`` placeholder. This is the
              endpoint that you later set on each |mongos|.
            - Set ``spec.security.tls.certsSecretPrefix``. |tls| is
              required for a sharded cluster with a managed load
              balancer.

            .. note:: ``externalHostname`` Depends on Your MongoDB Deployment

               You set ``externalHostname`` because your sharded
               cluster isn't managed by the same |k8s-op-short| that
               manages ``mongot``. Its value must be an externally
               resolvable hostname template that your shard ``mongod``
               members use to reach the Envoy load balancer. 

            The |k8s-op-short| creates a ``mongot`` StatefulSet for
            each shard in every member cluster and deploys an Envoy
            proxy for per-shard |sni| routing. To learn more about
            ``MongoDBSearch`` settings, see
            :ref:`k8s-fts-vs-settings`:

            .. literalinclude:: /includes/code-examples/search/13-search-sharded-multi-cluster/code_snippets/13_0320_create_mongodb_search_resource.sh
               :language: shell
               :copyable: true
               :linenos:

         .. step:: Configure search parameters on your external
            sharded cluster.

            You must set the search ``setParameter`` values yourself
            because your sharded cluster is external.

            On each shard's ``mongod`` members, point ``mongotHost``
            and ``searchIndexManagementHostAndPort`` at that shard's
            Envoy load balancer endpoint for the ``mongot`` group that
            the member is mapped to. This value is your
            ``spec.clusters[].loadBalancer.managed.externalHostname``
            template with the ``{shardName}`` placeholder resolved.
            Because each ``spec.clusters`` entry has its own
            ``externalHostname``, write a cluster-specific literal
            into each template. For example, if cluster
            ``clusterOne`` uses the template
            ``{shardName}.clusterOne.example.com``, the value for
            shard ``shardOne`` is ``shardOne.clusterOne.example.com``.

            On each |mongos|, point the same parameters at the
            cluster-level endpoint that you set on
            ``spec.clusters[].loadBalancer.managed.routerHostname``
            for that cluster. Unlike ``externalHostname``, this value
            has no ``{shardName}`` placeholder to resolve.

            .. note:: ``mongotHost`` Depends on Your MongoDB Deployment

               ``mongotHost`` and ``searchIndexManagementHostAndPort``
               are the ``mongod`` settings that must point to the
               operator-managed Envoy load balancer. Because your
               sharded cluster is external, set them to an externally
               resolvable URL. If your sharded cluster ran inside the
               same |k8s| cluster, you could instead use the |k8s|
               Service name of the Envoy load balancer.

            Set ``searchTLSMode`` to ``requireTLS`` and
            ``useGrpcForSearch`` to ``true``. To learn more about
            these parameters, see :ref:`k8s-fts-vs-settings`.

            You can set these parameters directly on each ``mongod``
            and |mongos| member or through the |com| UI. To use the
            |com| UI, follow the steps in
            :ref:`k8s-search-set-parameters-shard-multiple`, and set
            ``mongotHost`` and ``searchIndexManagementHostAndPort`` to
            the endpoints described earlier in this step.

            .. note:: Per-Shard Query Routing

               A search query for a shard must always reach the
               ``mongot`` group that syncs from that shard. The setup
               in this procedure is what enables this routing: the
               per-shard ``externalHostname`` gives each shard's
               ``mongod`` members a distinct endpoint, and the
               operator-managed Envoy load balancer uses |tls| |sni|
               to direct each shard's traffic to the matching
               ``mongot`` group. As a result, search queries never
               cross shard boundaries.
