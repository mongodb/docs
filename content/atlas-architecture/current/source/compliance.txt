.. _arch-center-compliance-certs:

Certifications and Compliance with Regulations
----------------------------------------------

|service-fullname| offers various features and configurations to 
help you address security, compliance, and privacy requirements.

|service-fullname| data platform undergoes rigorous independent 
third-party audits to verify its security, privacy, and organizational 
controls. {+service+} adheres to compliance frameworks including ISO/
IEC 27001, SOC2 Type II, PCI DSS, and others listed in our 
|atlas-trust|.  You can view and download attestations, compliance 
reports, and other compliance documentation in our 
`Customer Trust Portal <https://trust.mongodb.com/>`__.

.. _arch-center-compliance-atlas-gov:

MongoDB {+service+} for Government
-----------------------------------

MongoDB |atlas-gov| is a fully-managed multi-cloud developer data 
platform certified at FedRAMP® Class D (formerly called FedRAMP®
High). The platform:

- Uses a secure, fully-managed, dedicated FedRAMP® certified environment.
- Supports the unique requirements and missions of U.S. federal
  government agencies and their suppliers.
- Offers a set of features and the scalability needed to modernize legacy applications.

.. _arch-center-resource-policies:

{+arps+} 
-----------------------

To support your compliance requirements, {+arps+} offer
organization-wide controls for configuring and managing {+service+}
resources in alignment with your security, compliance, and
operational best practices. {+arps+} are controls that enable
:authrole:`Organization Owners <Organization Owner>` to constrain
the specific configuration options available to developers when
they create or configure |service| {+clusters+}.

Examples of compliance objectives that you can accomplish using
{+arps+} are:

- Limit cluster deployment to specific cloud platforms (|aws|,
  |gcp|, |azure|).
- Prohibit the use of wildcard IPv4 CIDR ranges (any ``/0`` mask,
  such as ``0.0.0.0/0`` or ``10.0.0.0/0``) to enforce stricter
  network controls.
- Prevent modifications to |vpc| peering and private endpoint
  connections across cloud providers.
- Prohibit traffic through public networks by requiring that the
  IP access list remain empty or by preventing additions to an
  existing IP access list.
- Enforce minimum and maximum cluster tiers and auto-scaling
  sizes across your organization.
- Require that a project has a maintenance window configured.

The following policy example prevents creation of clusters on
|aws|:

.. code-block::
   :copyable: true

   forbid (
      principal,
      action == ResourcePolicy::Action::"cluster.modify",
      resource
   )
   when { context.cluster.cloudProviders.contains(ResourcePolicy::CloudProvider::"aws") };

{+arps+} in |atlas-gov| work similar to that in commercial regions
except for features that are not available in |atlas-gov|.
Similarly, when a resource policy applies restriction to gov-only
regions, the values available are different from commercial e.g.
``us-gov-east-1`` vs ``us-east-1`` for |aws|. |atlas-gov| supports
|tls| 1.2 and 1.3 to encrypt connections. You cannot disable
|tls|. To learn more, see :atlas:`Atlas Resource Policies
</atlas-resource-policies/>`.

.. _arch-center-compliance-encryption:

Encryption
----------

You can implement encryption to amplify data security across all
stages of data handling. Encryption is one of the most common 
requirements for ensuring compliance with industry security standards, 
and {+service+} offers a robust set of encryption options to satisfy 
the requirements.

- By default, |service| encrypts data in transit. |service| requires
  |tls-ssl| to encrypt the connections to your databases. You can use
  {+arps+} to impose a minimum |tls| version or require a specific
  |tls| cipher suite configuration for {+cluster+} connections.
  MongoDB |atlas-gov| and databases hosted in AtlasGov support |tls|
  1.2 and 1.3 to encrypt connections. You cannot disable |tls|.

- By default, |service| encrypts all data at rest using 
  `cloud provider disk encryption <https://www.mongodb.com/docs/atlas/security-kms-encryption/>`__. When using {+service+} cloud backups,
  |service| uses |AES-256|
  encryption to encrypt all data stored in |s3| buckets in your |service|
  {+database-deployments+}.
  In addition, |service| supports using |aws| |kms|, |akv|, and |gcp| to
  encrypt storage engines and cloud provider backups. To learn more, see
  :atlas:`Encryption at Rest using your Key Management 
  </security-kms-encryption>`. 

- You can use :manual:`Queryable Encryption 
  </core/queryable-encryption/>` to secure queries on encrypted data on 
  a select set of sensitive fields in a document stored on MongoDB. 
  With Queryable Encryption, sensitive information remains protected 
  even when users run queries on data.

  Use  well-researched non-deterministic encryption schemes to maintain
  a balance between security and functionality.

  With {+qe+}, you can perform the following tasks:

  - Encrypt sensitive data fields from the client-side.
  - Store sensitive data fields as fully randomized encrypted data on the database 
    {+cluster+}-side, run with {+service+}.
  - Run expressive queries on the encrypted data.

  MongoDB completes these tasks without the server having knowledge of the data
  it's processing.

  When using Queryable Encryption, sensitive data is encrypted throughout its 
  lifecycle: in transit, at rest, in use,
  in logs, and backups. The data is only ever decrypted on the client-side,
  since only you have access to the encryption keys.

  You can set up {+qe+} using the following mechanisms:

  - :manual:`Automatic Encryption </core/queryable-encryption/>`
    enables you to perform encrypted read and write operations without
    having to add explicit calls to encrypt and decrypt fields. We recommend automatic encryption in most situations, as it streamlines the process of writing your client application. With automatic encryption, MongoDB automatically encrypts and decrypts fields in read and write operations.
  - :manual:`Explicit Encryption </core/queryable-encryption/fundamentals/manual-encryption/>` enables
    you to perform encrypted read and write operations through your MongoDB
    client library's encryption library. You must specify the logic for encryption
    with this library throughout your application. Explicit encryption provides fine-grained control over security, at the cost of increased complexity when configuring collections and writing code for MongoDB Client Libraries. With explicit encryption, you specify how to encrypt fields in your document for each operation you perform on the database, and you include this logic throughout your application.

    To learn more, see :manual:`Use Explicit Encryption </core/queryable-encryption/tutorials/explicit-encryption/>`.

.. _arch-center-compliance-data-sovereignty:

Data Regionalization
--------------------

{+service+} supports over 110+ regions across |aws|, |azure|, and 
|gcp|. This global distribution of supported locations allows you to 
provision clusters and store data that complies with your data 
localization requirements. You can also deploy your |service| clusters 
across multiple regions. When you deploy a 
:ref:`multi-region deployment paradigm 
<arch-center-paradigms-multi-region>`, you can partition your data to 
reside in distinct regions, each situated in a different geographical 
region. For example, you can store European customer data in Europe 
and U.S. customer data in the U.S. This allows you flexibility in your 
data localization choice, and reduces latency for users accessing data
from their respective regions. MongoDB |atlas-gov| supports only US
regions across AWS GovCloud, GCP Assured Workloads, Azure
Government, and AWS Commercial. To learn more, see **Supported
Cloud Providers and Regions** in the MongoDB |atlas-gov|
documentation.

MongoDB Atlas for Government Regions
------------------------------------

On MongoDB |atlas-gov|, you can create multi-cloud clusters across
US-based regions within the same FedRAMP® class level only.
Depending on the impact level of the data you must store, select
one of the following region types:

- **FedRAMP® Class D (High)**: AWS GovCloud (US) regions, GCP
  Assured Workloads (US) regions, and Azure Government (US)
  regions.

- **FedRAMP® Class C (Moderate)**: AWS Commercial (US) regions.

The following table lists the regions available in each class
level:

.. list-table::
   :widths: 15 40 45
   :header-rows: 1

   * - Provider
     - FedRAMP® Class C (Moderate)
     - FedRAMP® Class D (High)

   * - |aws|
     - Commercial: Northern Virginia (``us-east-1``), Ohio
       (``us-east-2``), Northern California (``us-west-1``),
       Oregon (``us-west-2``)
     - GovCloud: Northwestern US (``us-gov-west-1``), Eastern US
       (``us-gov-east-1``)

   * - |azure|
     - —
     - USGov Virginia, USGov Texas, USGov Arizona

   * - |gcp|
     - —
     - Assured Workloads: all standard US regions

You must designate projects for either FedRAMP® Class C (Moderate)
or FedRAMP® Class D (High) region usage upon creation. You cannot
deploy clusters across FedRAMP® Class D (High) and FedRAMP® Class C
(Moderate) regions in the same project.

.. note::

   Cross-cloud and cross-region impact levels are determined by
   the lowest region in your configuration. For example, if you
   have a cluster deployed across AWS Northern Virginia
   (``us-east-1``) and Azure Government (US Gov Virginia), your
   highest impact level tier is FedRAMP® Class C (Moderate).

If you have questions about which certification tier applies to
your workload, consult your company's compliance team. To learn
more about supported regions, see **Supported Cloud Providers and
Regions** in the MongoDB |atlas-gov| documentation.

.. _arch-center-compliance-backup-distribution:

Backup Snapshot Distribution
----------------------------

You can distribute backup snapshots and oplog data across multiple 
regions. For example, you can satisfy store backups in
different geographical locations to enable disaster recovery
in case of regional outages, or to maintain backups consistently with 
your data localization choices. To learn more, see 
:atlas:`Snapshot Distribution 
</backup/cloud-backup/snapshot-distribution/>`.

.. _arch-center-compliance-backup-compliance-policy:

Backup Compliance Policy
------------------------

You can use |bcp| in {+service+} and MongoDB |atlas-gov| to secure
business-critical data. This
feature prevents all backup snapshots and oplog data stored in 
{+service+} from being modified or deleted for a predefined retention 
period by any user, regardless of their {+service+} role.

This helps you guarantee that your backups are fully WORM (Write Once Read Many)-compliant.
Only a designated, authorized
user can turn off this protection after completing a verification
process with MongoDB support. This adds a mandatory manual 
delay and cooldown period so that an attacker cannot change the
backup policy and export the data. To learn more, see 
:atlas:`Configure a Backup Compliance Policy 
</backup/cloud-backup/backup-compliance-policy/>`.
