=========================
MongoDB Versions in Atlas
=========================

.. default-domain:: mongodb

.. facet::
   :name: genre
   :values: reference

.. meta:: 
   :keywords: Atlas versions, mongodb versioning, version management, major versions, latest version
   :description: Learn about MongoDB version options for Atlas clusters, including Auto Upgrades and Manual Upgrades. Compare availability by cluster type and understand how to select or change your cluster version.

.. contents:: On this page
   :local:
   :backlinks: none
   :depth: 2
   :class: singlecol

Your {+cluster+} type determines the method |service| uses to deliver
version upgrades to your cluster. |service| offers two methods for
receiving MongoDB versions: Auto Upgrades and Manual Upgrades.

Auto Upgrades and Manual Upgrades in Atlas
------------------------------------------

.. list-table::
   :header-rows: 1
   :widths: 30 70

   * - Upgrade method
     - What it does

   * - Auto Upgrades in Atlas
     - |service| delivers new major, minor, and patch releases to you
       automatically. In the {+atlas-ui+}, select
       :guilabel:`Latest Version With Auto Upgrades` under
       :guilabel:`Additional Settings`.

   * - Manual Upgrades in Atlas
     - You choose a specific major MongoDB version and control when you
       upgrade, while receiving patch releases automatically. In the
       {+atlas-ui+}, choose from the :guilabel:`Select a version`
       dropdown under :guilabel:`Additional Settings`.

Cluster types in |service| receive upgrades as follows:

- **For {+atlas-core-cluster+}s**, you can rely on Auto Upgrades, where
  |service| delivers new major, minor, and patch releases to you
  automatically, or use Manual Upgrades, where you choose a specific
  major MongoDB version and control when you upgrade. To learn how to
  select or change your version, see :ref:`scale-cluster-version`.

- **For {+atlas-infinite-cluster+}s**, |service| always uses Auto
  Upgrades. The :guilabel:`Latest Version With Auto Upgrades` option is
  always enabled, and you can't disable it in the {+atlas-ui+}. To learn
  how, see :ref:`database-edition-versions`.

- **For {+Free-clusters+} and {+Flex-clusters+}**, |service| upgrades
  them automatically and keeps them on a major version (currently,
  MongoDB 8.0).

The `MongoDB Software Lifecycle Schedules
<https://www.mongodb.com/legal/support-policy/lifecycles/>`__ page
describes the supported versions and end-of-life dates for MongoDB
Server releases.

For general guidance on MongoDB version numbering, release types,
and upgrade paths, see :ref:`versions-and-upgrade-paths`. 

For most |service| deployments, Auto Upgrades is the best way to
receive the latest MongoDB features and enhancements automatically as
|service| rolls them out.

For {+atlas-core-cluster+}s, you can choose to stay on a specific major
version. In this case, if you must validate a release before it reaches
production, stay on a major-version cadence.

Clusters that receive automatic upgrades, which include
{+atlas-infinite-cluster+}s and {+atlas-core-cluster+}s that you set to
Auto Upgrades, rely on :ref:`maintenance waves
<configure-maintenance-window>` to validate releases in a
non-production environment first.

The following table compares the two upgrade methods:

.. list-table::
   :header-rows: 1
   :widths: 20 40 40

   * - Consideration
     - Auto Upgrades
     - Manual Upgrades

   * - Automatic upgrades
     - Major, minor, and patch releases
     - Patch releases only

   * - Control over upgrade timing
     - No
     - Yes

   * - Version selection
     - Not available
     - Choose from the :ref:`available versions
       <create-cluster-version>`

   * - Switching cadence
     - Switch from Auto Upgrades to Manual Upgrades only in the window
       after a new major version releases. Available for
       {+atlas-core-cluster+}s only.
     - Switch {+atlas-core-cluster+}s to Auto Upgrades at any time by
       modifying the {+cluster+}

   * - Best for
     - Staying current with the latest features and improvements
       automatically
     - Direct control over release acceptance, such as
       coordinating versions across environments or certifying
       release contents before adoption

   * - Avoid if 
     - You require direct control over release acceptance, such as
       coordinating versions across environments or certifying
       release contents before adoption
     - You want to stay current with the latest features and
       improvements without managing upgrade timing yourself

To learn more about MongoDB Server versions in general, see :manual:`MongoDB Versioning </reference/versioning/>`.


.. _latest_version_with_auto_upgrades:

Auto Upgrades in Atlas
----------------------

When you :ref:`choose your cluster version <create-cluster-version>` and
select :guilabel:`Latest Version With Auto Upgrades` on an
{+atlas-core-cluster+}, |service| automatically upgrades your cluster
to the latest available MongoDB major or minor version, enables new
features as they become available, and upgrades patch releases through
a rolling process to maintain cluster availability. You can't select a
specific major, minor, or patch version.

On an {+atlas-infinite-cluster+}, :guilabel:`Latest Version With Auto
Upgrades` is always enabled, and you can't disable it.


Switching from Auto Upgrades to Manual Upgrades
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

If your {+atlas-core-cluster+} is on a minor version while on
:guilabel:`Latest Version With Auto Upgrades`, you can switch to a
major-version cadence only when the next major version becomes
available.

For example, if you opt in while MongoDB 8.3 is the latest release,
your {+atlas-core-cluster+} remains on the latest minor version until
MongoDB 9.0 is released. You can switch back to a major-version cadence
only in the window between the 9.0 release and the first 9.x minor
release. If you miss that window, you must wait until the next major
release cycle.

.. _manual_upgrades:

Manual Upgrades in Atlas
------------------------
If your {+atlas-core-cluster+} remains on a major version, you control
when major-version upgrades happen. You can
:ref:`upgrade the major version <upgrade-major-MongoDB-version>`
of your |service| cluster at any time by :ref:`modifying the cluster <scale-cluster>`.
Major versions also automatically receive patch release updates.

Before upgrading a major version in production, test your application
against a staging cluster and review compatibility changes in the
:ref:`release notes <server-release-notes-landing>`. If applicable,
rely on the :ref:`Stable API <stable-api>`.

End of Life for a Major Version
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
For the end-of-life policy for MongoDB versions, including
notification timing and upgrades after the cut-off date, see
:ref:`versions-and-upgrade-paths`.

.. _database-edition-versions:

Database Edition Versions
~~~~~~~~~~~~~~~~~~~~~~~~~

For the duration of public preview, {+atlas-infinite-cluster+}s run
the latest MongoDB 9.x version, using the :guilabel:`Latest Version
With Auto Upgrades` release option in the {+atlas-ui+}.
{+atlas-infinite-cluster+}s might run a later version than
{+atlas-core-cluster+}s, but these versions don't introduce
compatibility changes unless the :ref:`{+service+} changelog
<atlas-release-notes>` states otherwise. To learn about
{+atlas-infinite-full+}, see :ref:`atlas-infinite-edition`.

{+service+} updates an {+atlas-infinite-cluster+} about once a month.
You can't select a specific MongoDB version for an
{+atlas-infinite-cluster+}. To see the exact version number,
:ref:`view the activity feed <view-activity-feed>`.

.. _scale-cluster-version:

Select or Change the Cluster Version on {+atlas-core-cluster+}s
---------------------------------------------------------------

.. include:: /includes/fact-upgrade-best-practices.rst

{+service+} upgrades {+atlas-infinite-cluster+}s automatically. The
following steps apply to {+atlas-core-cluster+}s.

.. important::

   If your project contains a :ref:`custom role <mongodb-roles>`
   that uses actions introduced in a specific MongoDB version, you
   can't create a {+cluster+} with a MongoDB version earlier than
   that version unless you delete the custom role.

To select or change the cluster version:

.. procedure::
   :style: normal

   .. step:: Open the cluster configuration.

      - To set the version for a new cluster, complete the steps to
        :ref:`create a cluster <create-new-cluster>` and expand
        :guilabel:`Additional Settings`.
      - To change the version for an existing cluster, click
        :guilabel:`Edit Config` to open the cluster form and
        expand :guilabel:`Additional Settings`.

   .. step:: Select a version.

      From the :guilabel:`Select a version` dropdown, select the
      version for your cluster.

      |service| supports the following upgrade paths for
      {+atlas-core-cluster+}s:

      - MongoDB 7.0 to MongoDB 8.0
      - MongoDB 8.0 to MongoDB 9.0
      - MongoDB 8.0 to Latest Version With Auto Upgrades
      - MongoDB 9.0 to Latest Version With Auto Upgrades

      .. include:: /includes/extracts/fact-mongodb-version-downgrade-restriction-scale.rst
