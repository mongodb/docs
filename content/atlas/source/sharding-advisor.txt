=================
Sharding Insights
=================

.. meta::
   :description: Monitor sharded cluster performance with Atlas Sharding Insights, which provides dedicated metrics and observability for shard workloads, data distribution, and balancer activity.

.. default-domain:: mongodb

.. facet::
   :name: genre
   :values: tutorial

.. contents:: On this page
   :local:
   :backlinks: none
   :depth: 1
   :class: singlecol

*Requires M10+ sharded clusters running MongoDB 8.0 or later in
commercial Atlas deployments*

|service| |sharding-insights| provides dedicated monitoring and
observability for sharded clusters. The Sharding Insights dashboard
brings together sharding metadata, hardware usage, data
distribution, and balancer activity in one place. Use Sharding
Insights to view performance metrics, track workload distribution,
and identify issues across your sharded cluster's components.

|service| provides recommendations in :ref:`Performance Advisor
<performance-advisor>` to help you identify when sharding decisions
may improve your cluster's performance:

- When to shard a replica set.
- When to move a collection.
- When to shard an unsharded collection.
- When to add more shards.

Use the :ref:`shard-key-analyzer` to analyze candidate shard keys for
these recommendations.

|sharding-insights| provides a :guilabel:`Shards` view where you
can monitor individual shard performance, workload distribution,
and resource usage.

The page displays cluster summary information, active sharding
recommendations, and charts showing hardware and sharding-specific
metrics over time.

You can filter metrics by time range from 24 hours to 90 days, or
select a custom date range to analyze specific time periods.

Access |sharding-insights|
--------------------------

.. procedure::
   :style: normal

   .. include:: /includes/nav/steps-db-deployments-page.rst

   .. step:: Click the cluster name.

   .. step:: Click :guilabel:`Sharding Insights` in the cluster sidebar.

The |sharding-insights| page displays the :guilabel:`Shards` view,
where you can monitor metrics for individual shards.

Use the time range selector to choose a preset time range or select
a custom date and time range with the :guilabel:`Filter by Date and
Time` picker.

.. note::

   |sharding-insights| and Sharding Recommendations are enabled by
   default. Project owners and admins can toggle these features at
   the project level in :ref:`Project Settings <project-settings>`:

   - :guilabel:`Sharding Insights`: "See sharding health and
     metrics"
   - :guilabel:`Sharding Recommendations`: "Customized
     recommendations to improve your sharding configuration"

Cluster Summary
---------------

The |sharding-insights| page displays a summary section at the top
that shows key cluster overview information:

- **Total Shards**: Total number of shards in your cluster.
- **Balancer Status**: Current state of the balancer (enabled or
  disabled).
- **Balancing Window (UTC)**: Configured time window for balancer
  operations, if set.
- **Config Servers**: Overview of configuration server status.

This summary provides a quick overview of your cluster's sharding
configuration and current state.

Sharding Recommendations
------------------------

The :guilabel:`Recommendations` card below the cluster summary
displays active sharding recommendations for your cluster, with a
badge that indicates the number of recommendations. Expand the card
to view a summary of each recommendation. |service| recommends an
action when it detects:

- A large or growing unsharded collection that might benefit from
  sharding.
- Resource pressure on a shard that affects a collection, which
  might benefit from moving the collection to another shard.
- A cluster approaching storage or resource limits, which might
  benefit from additional shards.
- A replica set approaching scale limits, which might benefit from
  converting to a sharded cluster.

To view the details of a recommendation in :ref:`Performance
Advisor <performance-advisor>`, click the recommendation. To
evaluate candidate shard keys, click :guilabel:`Analyze Shard Keys`
to open the :ref:`Shard Key Analyzer <shard-key-analyzer>` in a new
tab.

If your cluster has no active recommendations, the card displays a
"No recommendations for now" message.

Shard Metrics
-------------

The :guilabel:`Shards` tab displays performance and resource metrics
for individual shards. By default, the dashboard shows CPU
usage, Reads, Writes, and Connections. You can select different
metrics from the dropdown menu to view additional hardware and
sharding-specific data.

The available metrics include hardware resource usage (CPU,
memory, connections, operations) and data distribution information
(data size, document count). These metrics help you identify
performance bottlenecks, capacity issues, and data distribution
imbalances across your shards.

Time Range Selection
--------------------

Select a time range to view historical metrics:

- **Preset Ranges**: Choose from 24 hours, 7 days, 30 days, or 90
  days.
- **Custom Range**: Select specific start and end dates using the
  calendar picker.

Historical data helps you identify trends, track changes over time,
and correlate issues with specific events.

|shard-key-advisor|
-------------------

|service| provides :ref:`Shard Key Analyzer
<shard-key-analyzer>`, a tool that helps you analyze and
select optimal shard keys for your collections. Access |shard-key-advisor|
through :ref:`Performance Advisor <performance-advisor>` to evaluate
candidate shard keys based on your cluster's query patterns and
workload characteristics.

You can also open |shard-key-advisor| from the
:guilabel:`Recommendations` card on the |sharding-insights| page by
clicking :guilabel:`Analyze Shard Keys`.

The analyzer appears in the Performance Advisor alongside sharding
recommendations and provides immediate analysis of:

- Cardinality: Uniqueness of values in candidate fields.
- Monotonicity: Whether field values increase or decrease over time.
- Frequency: Distribution of values across the field.

You can optionally enable query sampling for deeper insights into
read and write distribution patterns.

Prerequisites
-------------

To use |sharding-insights|, your cluster must meet the following
requirements:

- **Cluster Configuration**: Sharded cluster (not available for
  replica sets).
- **MongoDB Version**: MongoDB 8.0 or later.
- **Cluster Tier**: ``M10`` cluster tier or higher.
- **Project Settings**: |sharding-insights| is enabled by default.
  If the :guilabel:`Sharding Insights` page doesn't display in the
  cluster sidebar, confirm that the setting is enabled in
  :ref:`Project Settings <project-settings>`.
- **Environment**: Commercial Atlas deployments only.

Behavior
--------

When you navigate directly to the Sharding Insights URL, the page
preserves your selected tab and time range settings across browser
refreshes. This allows you to bookmark specific views or share URLs
with your team.

If you access Sharding Insights on a cluster that doesn't meet the
prerequisites, |service| displays a banner explaining why the feature
is unavailable instead of the Sharding Insights page.

Limitations
-----------

Sharding Insights has the following limitations in this release:

Deployment Support
~~~~~~~~~~~~~~~~~~

Sharding Insights does not support:

- Replica set deployments (only sharded clusters).
- Clusters running MongoDB versions earlier than 8.0.
- Clusters on tiers below ``M10``.
- Clusters using |service| Data Regionalization.
- Cloud Manager or Ops Manager deployments.
- Government cloud environments.

API and Automation Support
~~~~~~~~~~~~~~~~~~~~~~~~~~~

This release does not support:

- |service| Administration API access to Sharding Insights data.
- Terraform provider support for Sharding Insights configuration.
- MongoDB MCP Server integration for Sharding Insights metrics.

These capabilities might be added in future releases.

Feature Scope
~~~~~~~~~~~~~

Future releases will include these advanced features:

- Detailed collections aggregation views.
- Advanced ``mongos`` performance analytics.

Important Considerations
------------------------

Before you act on recommendations or make sharding changes, review
these important considerations:

Sharding Decisions
~~~~~~~~~~~~~~~~~~

- **Permanent Change**: Converting a replica set to a sharded
  cluster is a permanent architectural decision that cannot be
  reversed.
- **Planning Required**: Review the :manual:`sharding documentation
  </sharding/>` and plan your shard key strategy before you shard a
  collection.
- **Shard Key Selection**: Choose a shard key that supports your
  query patterns and provides good data distribution. See
  :manual:`Choose a Shard Key </core/sharding-choose-a-shard-key/>`
  to evaluate potential shard keys.
- **Test Before Production**: Test your application with the selected
  shard key on a sharded cluster before applying it to production.
  Moving from a replica set to a sharded cluster may expose
  differences in functionality and performance. Validate that your
  application handles these differences appropriately.

Write Operation Semantics
~~~~~~~~~~~~~~~~~~~~~~~~~~

Sharded clusters have different write operation semantics than
replica sets:

- **Multi-Document Operations**: Use
  :method:`~db.collection.updateMany()` and
  :method:`~db.collection.deleteMany()` only for idempotent writes on
  sharded collections. These operations may execute more than once on
  some documents if there are network errors or failovers during
  execution.
- **Retryable Writes**: MongoDB provides :ref:`retryable writes
  <retryable-writes>` for single-document operations to handle
  transient failures, but multi-document operations require careful
  design.
- **Write Concern**: Review your application's :ref:`write concern
  <write-concern>` settings to ensure they align with your durability
  requirements in a sharded environment.

Review the :ref:`sharding operational restrictions
<sharding-operational-restrictions>` before you shard your cluster.

Network Considerations
~~~~~~~~~~~~~~~~~~~~~~

- **PrivateLink Impact**: If your cluster uses PrivateLink,
  converting from a replica set to a sharded cluster will completely
  block connectivity to the shards. Your application will experience
  downtime until it is restarted and reconnects to the ``mongos``
  router.
- **Connection Updates**: When you convert from a replica set to a
  sharded cluster, your application must restart to reconnect to the
  ``mongos`` router. If your application uses an SRV connection
  string, no changes to the connection string are needed, but the
  application restart is still required. Adding shards to an existing
  sharded cluster does not require an application restart.

Collection Movement Constraints
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

When you move collections between shards:

- **One at a Time**: Only one collection can be moved at a time.
- **No Write Blocking**: Collection moves use resharding, which
  allows write operations to continue during the move.
- **Destination Capacity**: The destination shard must have
  sufficient storage and resource capacity.
- **Operation Time**: Large collections might take significant time
  to move.
