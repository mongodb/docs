# Report template

Output is a pointer list, not a report: orient, then point.

**No em dashes anywhere in the output.** Use a period, comma, or "because" or "so" instead of breaking a sentence with a dash.

**Use bold labels and blank lines between items.** This is read in a GitHub PR description/comment, not a terminal, so give it room: bold the label of each line (`**Confidence:**`, `**Testing status:**`), and put a blank line between each bulleted item so the list doesn't read as one dense block.

**Keep the opening orientation to one line, plus a second if there's a collateral change to name.** State what's being compared and what the docs PR does. Skip meta-commentary about the ticket itself (e.g. that it's auto-generated, thin, or that no engineering PR exists) unless that fact is the reason confidence is lower, in which case fold it into the confidence line instead, not the opener. If the PR contains a collateral change (see Stage 2: something done only to keep the code building against an upstream bump), name the cause in one clause here. This is the only place a causal aside belongs; do not smuggle it into a `[Verify]`/`[Gap]` bullet instead, which should stay a flat claim plus where to check it.

```
## Tech Reviewer Suggestions

This report cross-references <docs PR> against <eng PR / Jira / release notes / current source>. <One-line synthesis of what the docs PR does, plain language>.

**Confidence:** <low/med/high>. <Plain statement grounded in content of what checks out, not an invented count, e.g. "Defaults, timeline, and removal version all match the eng change.">

**Testing status:** <one clause, only if code examples changed, e.g. "New Grove test added (path)." or "No Grove tests found for the new examples.">

**Suggested areas of investigation:**

- **[Gap]** <what's missing, ≤1 line>. <Why it's only visible in the diff/source, ≤1 line>.

- **[Verify]** <the claim, ≤1 line>. <Where to check it, ≤1 line>.

- **[Confirm]** <the completeness question, ≤1 line>?

Tech Reviewer Suggestions generated by the pr-coverage-check skill and reviewed by the author. These are suggestions and require human review.
```

Do not include a "Not a concern" section or otherwise list changes that were checked and found fine. That belongs in the confidence line, in one clause, if at all, not as its own section, per design commitment 4: the reviewer already has the diff open.

## Confidence rubric

- **High**: every public-contract change unit maps directly to a diff line with no inference required.
- **Medium**: one or more units required inference, or the source is Mode B (Jira/release notes, not a diff).
- **Low**: heavy inference throughout, or the ticket/diff is too thin to check units against.

## Worked example (illustrative, not a real ticket)

```
## Tech Reviewer Suggestions

This report cross-references docs PR #123 against the driver's 5.10.0 release notes. The docs PR adds a note that `maxStalenessSeconds` now rejects values under 90.

**Confidence:** high. The 90-second floor and the error name match the eng diff.

**Testing status:** New Grove test added (code-example-tests/node/.../tests/read-pref.test.js).

**Suggested areas of investigation:**

- **[Gap]** Docs don't mention the new `InvalidStalenessError` thrown below the floor. Only visible in driver.go:412, not in the ticket.

- **[Verify]** Docs say the floor "applies to secondaries only". Check driver.go:398, which reads as applying cluster-wide.

Tech Reviewer Suggestions generated by the pr-coverage-check skill and reviewed by the author. These are suggestions and require human review.
```

## Constraints

Apply on top of the design commitments in SKILL.md; commitment 2's "evidence over scores" and commitment 3's "precision over recall" already govern this section, not restated here.

- **Lead with the writer's action, not the eng ticket.** "The docs PR adds a note describing X", not "Eng ticket Y adds X."
- **One line per item, two absolute max (Gap/Verify/Confirm).** If it takes more than that to state, it has not cleared the inclusion test yet; sharpen it or drop it. The Testing note may take one extra bullet line for a specific action item, but no more.
- **Nothing after the closing line.** No summary of what's empty, no restating why items cleared the inclusion test, no closing question to the writer beyond the Stage 6 confirm step. If a bullet category is empty, simply omit it; do not explain the absence.
- **Total list ≤5 items.** If more clear the inclusion test, that itself is a signal the change may be too large or too loosely scoped for a single pass.
- **Skip "docs changes with no eng counterpart" entirely** unless one asserts new behavior not backed by the eng change, or is a collateral change (Stage 2). A collateral change has no eng counterpart by definition, so this constraint must not be used to drop it. Name its cause in the opener instead of skipping it.
