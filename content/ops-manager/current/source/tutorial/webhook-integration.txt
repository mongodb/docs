======================================
Integrate with Webhooks in Ops Manager
======================================

.. default-domain:: mongodb

.. facet::
   :name: genre
   :values: tutorial

.. contents:: On this page
   :local:
   :backlinks: none
   :depth: 2
   :class: singlecol

You can configure |mms| to send alert notifications to a webhook
endpoint as |http| POST requests for programmatic processing.
Webhooks allow you to integrate |mms| alerts with custom
monitoring systems, incident management platforms, or automation
workflows.

Required Access
---------------

To integrate |mms| with webhooks, you must have
:authrole:`Project Monitoring Admin` access to the project.

.. _authenticate-webhook-requests:

Authenticate Webhook Requests
-----------------------------

You can authenticate webhook requests with the following methods:

- **Webhook secret**: |mms| uses the secret to generate the
  ``X-MMS-Signature`` header. |mms| doesn't send the secret
  itself as an authentication header or bearer token. To learn
  how to verify the signature, see
  :ref:`verify-webhook-requests`.

- **OAuth 2.0 client credentials**: |mms| obtains a bearer access
  token from your OAuth 2.0 token endpoint and sends it in the
  ``Authorization`` header. To configure this method, see
  :ref:`configure-webhook-integration`.

You can use one method, both, or none. If you configure both, |mms|
includes the ``Authorization`` and ``X-MMS-Signature`` headers in the
same request.

|mms| caches the OAuth 2.0 access token and refreshes it when the
token expires. If your webhook endpoint returns a ``401``
response, |mms| refreshes the token and retries the request once.

Custom Headers Template Behavior
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

If you configure a custom headers template, it replaces the
default headers in the request. |mms| doesn't add the
``X-MMS-Signature`` or ``Authorization`` headers for you. To
include either header, add it to your template:

- ``"X-MMS-Signature": "${signature}"``

- ``"Authorization": "Bearer ${oauthToken}"``

To learn more about webhook templates, see
:ref:`om-webhook-templating`.

Other Authentication Methods
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

If the webhook secret and OAuth 2.0 client credentials don't meet
your needs, you can handle authentication in one of the following
ways:

- **Query Parameters**: Include authentication credentials in
  the :guilabel:`Webhook URL` as query parameters. For example:
  ``https://example.com/webhook?token=your-auth-token``

- **IP Access List**: Configure your webhook endpoint to accept
  requests only from your |mms| instance's IP addresses.

- **Reverse Proxy or API Gateway**: Use a reverse proxy or
  |api| gateway that handles authentication before forwarding
  requests to your webhook endpoint.

.. _verify-webhook-requests:

Verify Webhook Requests
~~~~~~~~~~~~~~~~~~~~~~~

To verify that a webhook request originated from |mms|,
validate the ``X-MMS-Signature`` header:

.. procedure::
   :style: normal

   .. step:: Retrieve the ``X-MMS-Signature`` header value from the incoming request.

   .. step:: Calculate the Base64-encoded |hmac|-SHA-1 signature of the request body using your webhook secret.

   .. step:: Compare your calculated signature with the ``X-MMS-Signature`` header value.

      If they match, the request is authentic.

.. _configure-webhook-integration:

Configure a Webhook Integration
-------------------------------

.. procedure::
   :style: normal

   .. step:: Navigate to the :guilabel:`Project Integrations` page.

      a. If it is not already displayed, select the
         organization that contains your desired project from
         the |ui-org-menu| in the navigation bar.

      #. If it is not already displayed, select your desired
         project from the :guilabel:`Projects` menu in the
         navigation bar.

      #. Click :guilabel:`Integrations` in the left navigation
         panel under the :guilabel:`Settings` heading.

   .. step:: Click :guilabel:`Configure` for :guilabel:`Webhook Settings`.

   .. step:: Enter the webhook URL.

      In the :guilabel:`Webhook URL` field, enter the endpoint
      |url| where |mms| should send alert notifications.

   .. step:: Configure authentication.

      Enter at least one of the following authentication
      options:

      - :guilabel:`Webhook Secret`: Enter a secret key. |mms|
        uses this secret to generate the ``X-MMS-Signature``
        header for request verification.

      - :guilabel:`OAuth2 Token URL`, :guilabel:`OAuth2 Client
        ID`, and :guilabel:`OAuth2 Client Secret`: Enter the
        token endpoint that |mms| calls to obtain an access
        token, and the credentials for the application that you
        registered with your OAuth 2.0 provider. Set all three
        values together, or leave all three empty.

      You can use both options together. To learn more, see
      :ref:`authenticate-webhook-requests`.

   .. step:: Click :guilabel:`Save`.

To send alerts to your webhook, configure alert notifications.
To learn more, see :ref:`configure-alerts`.

Request Body
------------

The request body contains a |json| document that uses the same
format as the |mms| |api|
:doc:`Alerts resource </reference/api/alerts>`. The payload
includes key fields such as:

- ``id``: Unique identifier for the alert.
- ``eventTypeName``: Type of event that triggered the alert.
- ``created``: Timestamp when the alert was created.
- ``status``: Current status of the alert (for example, ``OPEN``,
  ``CLOSED``).
- ``humanReadable``: Human-readable description of the alert.

For a complete list of fields, refer to the
:doc:`Get One Alert </reference/api/alerts-get-alert>`
endpoint documentation.

Example Webhook Payload
~~~~~~~~~~~~~~~~~~~~~~~

The following example shows a sample webhook payload for a
metric threshold alert:

.. code-block:: json

   {
     "id": "5d1b6f8e8c2e4e2d3c4a5b6c",
     "groupId": "5d1b6f8e8c2e4e2d3c4a5b6d",
     "eventTypeName": "OUTSIDE_METRIC_THRESHOLD",
     "status": "OPEN",
     "created": "2024-01-15T10:30:00Z",
     "updated": "2024-01-15T10:30:00Z",
     "lastNotified": "2024-01-15T10:30:00Z",
     "humanReadable": "Disk space used on data partition is
       95.2%.",
     "metricName": "DISK_PARTITION_SPACE_USED_DATA",
     "currentValue": {
       "number": 95.2,
       "units": "RAW"
     }
   }

Customize Webhook Templates
---------------------------

You can customize the request headers and body content using
FreeMarker templates. For detailed information about webhook
templating, including available template variables, regex
helpers, and examples, see
:doc:`Configure Webhook Templating
</tutorial/webhook-templating>`.

Limitations
-----------

When you use webhook integrations, consider the following
limitations:

Alert Severity Not Included
~~~~~~~~~~~~~~~~~~~~~~~~~~~

The webhook payload does not include the alert severity level
that you configure in |mms|. To retrieve the configured
severity, make an additional call to the
:doc:`Get One Alert Configuration
</reference/api/alert-configurations-get-config>` endpoint using
the ``alertConfigId`` from the webhook payload.

No Manual Test Alerts
~~~~~~~~~~~~~~~~~~~~~

|mms| does not provide a way to trigger test alerts manually.
To test your webhook endpoint, you can temporarily set up an
alert with conditions that you can trigger, such as:

- A low disk space threshold on a test deployment.
- A connection count threshold that you can trigger by opening
  multiple connections.
- A replication lag threshold on a test replica set.

After you confirm your webhook receives alerts correctly, you
can delete the test alert configuration.

Firewall Configuration
----------------------

Since |mms| is self-hosted, ensure your network allows
outbound |http| requests from the |mms| server to your
webhook endpoint. If your webhook endpoint is behind a
firewall, add the |mms| server's IP address to the
endpoint's IP access list.

Troubleshoot Webhook Delivery Issues
-------------------------------------

If your webhook does not receive alerts:

.. procedure::
   :style: normal

   .. step:: Verify that the webhook URL is correct and accessible from the |mms| server.

   .. step:: Check that your firewall allows outbound requests from the |mms| server to the webhook endpoint.

   .. step:: Ensure your webhook endpoint returns a 2xx HTTP status code.

      |mms| considers other status codes as failures.

   .. step:: Review your alert configuration to ensure alerts are enabled and the webhook is selected as a notification method.

   .. step:: Check the :guilabel:`Activity Feed` in the |mms| UI for any webhook delivery errors.
