=============================================
Telemetry in Ops Manager 8.0.27 and Earlier
=============================================

.. default-domain:: mongodb

.. meta::
   :description: Ops Manager telemetry for 8.0.27 and earlier: how the anonymous weekly usage report works, what data it collects, and how to view, enable, or disable it.

.. contents:: On this page
   :local:
   :backlinks: none
   :depth: 2
   :class: singlecol

Telemetry collects anonymous usage information about your |mms|
installation and sends it to MongoDB once a week. |mms| enables
collecting and sending telemetry by default.

This page applies to |mms| 8.0.27 and earlier. Starting in |mms|
9.0.2 and 8.0.28, product usage telemetry replaces the weekly
anonymous report. Product usage telemetry collects configuration and
health metadata daily instead, ties the data to your Enterprise
Advanced account, and requires an active telemetry exemption to turn
off. To learn how it works, see :ref:`Product Usage Telemetry
<om-telemetry-overview>`.

.. note::

   Telemetry has a separate setting from product usage telemetry. If
   you turn off telemetry in |mms| 8.0.27 or earlier, the setting
   doesn't carry over. Product usage telemetry applies after you
   upgrade to 9.0.2 or 8.0.28.

About Telemetry
---------------

Telemetry is an automated, anonymous usage report that |mms|
generates and sends to MongoDB once a week.

Telemetry describes:

- How you configure and run your |mms| installation.
- The MongoDB deployments that |mms| manages.

Telemetry doesn't include data that |mms| can use to uniquely
identify you or your organization.

Telemetry Purpose and Usage
---------------------------

MongoDB uses telemetry data to understand how customers configure
and use |mms| and the MongoDB deployments that it manages. This
information helps MongoDB:

- Identify the most common deployment patterns.
- Understand the size and topology of managed deployments.
- See which backup mechanisms and infrastructures are most common.

MongoDB uses these insights to prioritize product improvements that
benefit the most customers.

Telemetry Data Collected
------------------------

Telemetry data describes your |mms| installation and each
MongoDB deployment that |mms| manages.

Installation-Level Data
~~~~~~~~~~~~~~~~~~~~~~~

Telemetry includes information about your |mms| installation, such
as:

- A static, unique identifier for the |mms| installation.
- The |mms| version.
- The operating systems that run on the |mms| hosts.
- The number of |mms| instances in this installation.
- The number of AppDB nodes.
- The number of backup daemons running.
- The authentication method that |mms| uses.
- The infrastructure type that hosts |mms|.
- CPU cores and memory provisioned for each |mms| host.
- The number of projects and organizations that exist in this
  installation.

Deployment-Level Data
~~~~~~~~~~~~~~~~~~~~~

Telemetry also includes information about each MongoDB deployment that
|mms| manages, such as:

- A static, unique identifier for the deployment.
- The MongoDB version or versions that the deployment uses.
- The deployment type.
- The number of nodes and, for sharded clusters, the number of shards.
- The total data size for the deployment, not including local metadata.
- The MongoDB edition used by the deployment.
- Whether |tls| is enabled.
- The authentication method that the deployment uses.

For the complete field list and types, see the telemetry response
schema in :ref:`Retrieve Telemetry Data
<om-get-telemetry-collection-details>`.

When Telemetry Runs
-------------------

If telemetry is enabled, |mms| schedules a recurring job that
collects and sends telemetry data once every seven days.

If you install or upgrade to |mms| 8.0.17 or later in the 8.0
series, |mms| enables telemetry by default. The same applies to
7.0.20 or later in the 7.0 series. |mms| waits seven days before it
sends the first telemetry snapshot. This grace period gives you time
to review and, if needed, disable telemetry before any data is sent.

|mms| uses persisting identifiers for telemetry across
restarts and upgrades. If you reinstall |mms|, it generates new
identifiers.

View Telemetry Data
-------------------

You can view the telemetry data that |mms| plans to send before
|mms| sends it.

Use the Diagnostics Output
~~~~~~~~~~~~~~~~~~~~~~~~~~

|mms| includes telemetry data in its diagnostics output. The
diagnostics output contains internal diagnostic information about your
|mms| installation, including the telemetry payload.

To review telemetry data:

.. procedure::
   :style: normal

   .. step:: Open the |mms| Config page

      From the |mms| UI, click :guilabel:`Admin`,
      :guilabel:`General`, :guilabel:`Ops Manager Config`.

   .. step:: Download the diagnostics output

      On the :guilabel:`Permissions` tab, in the :guilabel:`Details`
      section, click :guilabel:`Download` next to :guilabel:`Current
      Collected Data`.

   .. step:: Review the telemetry data

      Extract the diagnostics output and locate the telemetry data in
      the archive.

Only a subset of the diagnostics data is sent as telemetry. Review the
telemetry subset in the archive to see the data values that |mms|
plans to send in the next telemetry snapshot.

Use the Telemetry API
~~~~~~~~~~~~~~~~~~~~~

You can also use the telemetry API to view the telemetry status and
payload that |mms| plans to send.

The :ref:`Retrieve Telemetry Data <om-get-telemetry-collection-details>`
endpoint returns:

- A flag that indicates if telemetry is enabled.
- The date and time when |mms| last sent telemetry successfully.
- The date and time when |mms| schedules the next telemetry job.
- The telemetry data object for the next snapshot.

Control Telemetry Collection
----------------------------

You can enable or disable telemetry collection for your |mms|
installation at any time.

.. important::

   Telemetry is either enabled or disabled for the entire
   installation. You can't enable or disable individual telemetry
   fields.

Use the UI
~~~~~~~~~~

Administrators can configure telemetry from the |mms| UI.

.. procedure::
   :style: normal

   .. step:: Open the |mms| Config page

      From the |mms| UI, click :guilabel:`Admin`,
      :guilabel:`General`, :guilabel:`Ops Manager Config`.

   .. step:: Open the Permissions tab

      Click the :guilabel:`Permissions` tab to view the
      :guilabel:`Usage Information Collection` setting.

   .. step:: Enable or disable telemetry

      Use the :guilabel:`Usage Information Collection` control to
      enable or disable telemetry.

If you disable telemetry, |mms| stops sending telemetry snapshots
starting with the next scheduled run.

Use the API
~~~~~~~~~~~

You can also control telemetry collection by using the telemetry
API.

You can use the :ref:`Toggle Telemetry Status
<om-patch-toggle-telemetry-status>` endpoint to:

- Enable telemetry by setting the ``enabled`` field to ``true``.
- Disable telemetry by setting the ``enabled`` field to ``false``.

Network and Connectivity
------------------------

Telemetry requires that your |mms| hosts can reach the
MongoDB telemetry ingestion endpoint.

.. note::

   |mms| installations that run in air-gapped environments or
   behind restrictive firewalls might be unable to send telemetry
   data, even if telemetry is enabled.

MongoDB stores ingested telemetry in an internal system and uses it in
aggregate form to improve |mms| and related products.
