Solution Overview
-----------------

Traditional lending systems rely on disconnected legacy applications
that were not built for real-time data, automation, or digital-first
customer experiences. Customers now expect instant decisions and full
transparency, while lenders manage rising risk, regulatory pressure, and
growing data complexity.

This solution shows you how to build a modern digital lending system. It
replaces a linear, paper-heavy process with a data-driven, real-time
workflow that connects origination, underwriting, approval, funding, and
servicing into one pipeline.

Why MongoDB?
~~~~~~~~~~~~~~~

Agentic workflows generate several distinct types of state: operational
records, embeddings, activity metrics, and the agents' own memory.
Separate systems for each type add infrastructure and create consistency
problems between them. |service-fullname| stores all of these in one modern data 
platform with one query language, which reduces the integration work.

**Schema flexibility and the document model**

- A loan application accumulates detail through its lifecycle from borrowers,
  documents, credit data, risk metrics, and decisions. It stays one document
  that grows, instead of an entity spread across a dozen tables joined on
  every read.

- Polymorphic detail fits naturally in this model. Employment income and
  self-employment income carry different fields inside the same array,
  with no nullable columns and no subtype tables.

- Agent-generated fields appear without migrations. When the underwriter
  agent adds a new metric, it writes the field directly with no coordinated
  schema change, and no deployment ordering.

**Atlas Vector Search for Semantic Understanding**

- Embeddings live on the documents they describe. One query returns a
  semantic match together with its business data, which removes the need
  to keep a database and a separate vector index in sync.

- Pre-filtering scopes a search to a single application. This keeps one
  borrower's documents out of another's results, turning an access-control
  requirement into a search parameter instead of application logic.

**Aggregation Pipelines for Explainable Scoring**

- Risk scoring runs where the data lives. One pipeline joins credit and
  income records, derives the ratios, and returns a bounded score, with no
  data transfer to application code.

- Because the calculation is declarative, the solution exposes each stage
  to the interface. Explainability becomes part of the implementation, not
  a separate reporting effort.

**Change Streams for Real-Time Interfaces**

- The officer queue, the borrower status tracker, and the activity log all
  read change events from the database. No separate message broker sits
  between a committed write and the interface that shows it.

- Streams resume from a stored position after a connection failure, so a
  transient network fault does not create a gap in the audit feed.

**LangGraph MongoDB Checkpointer for Agent Memory**

- Workflow state persists to Atlas at each step. An application paused for
  human review survives restarts and redeployments, and resumes with full
  context.

Together, these capabilities let a single platform carry an agentic
lending workflow end to end, from document intake through underwriting,
human review, and portfolio monitoring, without the integration surface
a multi-database architecture requires.


Reference Architectures
-----------------------

The solution consists of the following:

- **Frontend**: The experience layer: Borrower Portal, Loan Officer
  Dashboard, Demo Flow, and Renewal Dashboard.

- **Backend**: A FastAPI service that hosts the LangGraph agent pipeline
  and exposes it over REST, SSE, and WebSocket.

- **MongoDB Atlas**: The intelligent data platform for operational records,
  vectors, time series metrics, real-time change events, and agent memory.

- **AI and observability**: Amazon Bedrock (Claude Haiku 4, tool use for
  structured output), and Voyage AI (multimodal embeddings).

Agents
~~~~~~~

The LangGraph Agent Pipeline is composed by the following:

.. figure:: /includes/images/industry-solutions/agentic-lending-flow.svg
   :alt: Agentic Flow
   :lightbox:

   Figure 2. Agentic Flow. 

- **Supervisor**: Inspects workflow state after every step and decides
  what happens next: fan out to gather data, proceed to underwriting,
  escalate to a human, or complete. It owns the retry policy and the pause
  condition when an application is blocked on borrower input.

- **Document verifier**: Checks completeness against required document
  types, flags failed extractions, detects duplicate uploads by hashing
  extracted text, and cross-checks applicant names across documents.

- **Credit puller**: Retrieves bureau records for each borrower on the
  application and attaches the scores to workflow state.

- **Loan application agent**: Synthesizes gathered documents and credit
  data into a coherent application narrative and advances the
  application's status.

- **Underwriter**: Runs the risk aggregation, computes affordability
  ratios and the stress test, retrieves governing policy through vector
  search, and produces a structured recommendation: approve, decline, or
  escalate.

- **Application assistant agent**: Operates outside the pipeline and
  answers borrower questions using context from their own file and the
  policy corpus.

The supervisor dispatches the document verifier and credit puller
concurrently. Document extraction and credit retrieval have no
dependency on each other, so overlapping them removes the largest
sequential wait in the pipeline.

.. figure:: /includes/images/industry-solutions/agentic-lending-agents.svg
  :alt: Agentic Flow Diagrams
  :lightbox: 

  Figure 3. LangGraph Agent Pipeline.


Autonomy and human oversight (HITL)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The supervisor runs under one of four autonomy modes: observe, suggest,
bounded, or auto. The default, bounded, lets the pipeline act
autonomously within policy limits and escalates to an officer when a
threshold trips — for example, a purchase price above $500K or GDS/TDS
ratios past policy limits. Every officer decision (approve, decline, or
modify and continue) carries the officer's ID and writes to an immutable
audit collection. The pipeline resumes through the LangGraph
checkpointer, so a human review does not lose workflow state.

-------------------

stores all of them:

Keeping these together is what makes the solution manageable. A
conventional stack places the operational records in a relational
database, the vectors in a dedicated vector store, the metrics in a time
series database, and the agent state in a cache — then spends most of
its engineering effort keeping four systems consistent.


Build the Solution
------------------

This section shows you how to implement the agentic lending solution.
For the full implementation guide, clone the repository and follow the
setup instructions in the `GitHub README
<https://github.com/mongodb-industry-solutions/fsi-agentic-lending>`__.

Building this solution follows these steps:

.. procedure::
   :style: normal

   .. step:: Provision the data platform. 
      
      - Create an Atlas cluster and the collections listed in S3. 
      - Build a vector search index over the policy and document
        embeddings, add TTL indexes for the pipeline lock collection. 
      - Configure the payments and agent activity collections as time
        series.


   .. step:: Connect the AI providers.

      - Wire Amazon Bedrock for LLM calls (Claude Haiku 4 with tool use for
        structured output) and Voyage AI for multimodal embeddings. 
      

   .. step:: Build the agent pipeline in LangGraph.

      - Implement the supervisor and its routing logic, the parallel
        document-verifier and credit-puller nodes, the underwriter's
        seven-stage risk aggregation, and the HITL interrupt/resume gate
        backed by MongoDBSaver checkpoints. 

        - Checkpoints also work as a forensic record. You can reconstruct what the agents knew at the
          moment of a decision, a different artifact from a log of what they said. 

        - Since a mortgage application is a long-running,
          multi-day process with human-in-the-loop steps (underwriter
          review, document re-submission, conditional approval).
          MongoDBSaver persists the entire graph state after each execution.
          That means an application can sit paused for 3 days waiting on a
          borrower's pay stub, and when it resumes, the graph picks up
          exactly where it left off with full state intact.

          An example setup:

          .. code-block:: python

             from langgraph.checkpoint.mongodb import MongoDBSaver 
             from langgraph.graph import StateGraph 
             from pymongo import MongoClient 
             
             client = MongoClient(ATLAS_URI) 
             checkpointer = MongoDBSaver(client, db_name="lendflow") 
             
             graph = StateGraph(MortgageState) 
             # ... add_node(intake), add_node(document_verification), 
             # add_node(underwriting), add_node(human_review) ... 
             app = graph.compile(checkpointer=checkpointer)
        
          If the graph hits an interrupt() at the human-review node,
          invoke returns with state paused. FastAPI can return a 202 to
          the client immediately. When the underwriter approves via a
          separate endpoint days later, you just invoke again with the
          same config and new input, and LangGraph resumes from the last
          checkpoint, not from scratch.


   .. step:: Expose the pipeline through FastAPI.

      - Add REST endpoints for application and officer actions, SSE for
        status and activity streams, and a WebSocket channel for the
        officer queue.

   .. step:: Frontend set up.

      - Build the frontend experiences in Next.js.

   .. step:: Seed demo data and run.

      - Generate the seeded borrower profiles and their synthetic documents.
      - Run locally with Docker Compose or deploy to Kubernetes for staging and production.
 
.. note:: 

   This demo implementation ships a Canadian mortgage configuration,
   including an OSFI B-20 style stress test and GDS/TDS affordability
   ratios. The rules live in one function and one collection, so you
   reconfigure the solution for a different market by changing the
   underlying configuration-as-data MongoDB document rather than rewriting
   the code. 


Key Learnings
-------------

- **Unify agent state with a single platform, MongoDB Atlas**: Agentic
  workflows produce operational records, embeddings, and checkpointed
  memory. Storing all four in Atlas removes the integration and
  consistency work of a four-database stack.

- **Model the loan as one evolving document with the Flexible Document
  Model**: The document model lets borrower, credit, and risk data
  accumulate on a single record through the whole lifecycle, so new
  agent-written fields and polymorphic income types need no schema
  migration.

- **Query vectors next to the data they describe with Atlas Vector
  Search**: MongoDB stores each embedding as a field on the document it
  describes, and Atlas Vector Search queries it there. One query returns
  the semantic match and its business data together, and scoping the
  search to a single application keeps one borrower's documents out of
  another's results.

- **Make risk scoring explainable and configurable by design with the
  Aggregation Framework**: Running the risk calculation as a declarative
  aggregation pipeline exposes every stage of the score, so explainability
  comes from the implementation rather than a separate reporting layer.

- **Persist agent memory for reliable human review with the LangGraph
  MongoDB Checkpointer**: The checkpointer lets a workflow paused for
  officer review survive restarts and resume with full context, and
  doubles as an audit trail of what the agents knew when they made a
  decision.
