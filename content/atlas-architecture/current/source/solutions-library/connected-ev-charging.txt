Solution Overview
-----------------

Whether you are an automotive OEM, an energy or utility provider, or a
mobility tech startup, connected electric vehicle (EV) charging requires
bringing together data that changes at different speeds and powers
different parts of the charging experience.

This data includes:

- Station locations and connector capabilities.

- Station availability and active sessions.

- Pricing.

- Operational events.

As charging networks grow, keeping this data consistent and accessible
across driver-facing and operational experiences becomes increasingly
important for delivering reliable services and making informed
decisions.

Drivers expect accurate answers before they choose a charger. Operators
need to detect faults and act before drivers notice them. When this data
lives in separate systems, both groups wait, and AI agents lack the
context to help.

This solution demonstrates how a unified operational data layer can
bring these workloads together in MongoDB. A shared data foundation
supports real-time charging experiences and provides operators with a
consistent view of station and session activity.

Within a single application architecture, the solution manages:

- Station discovery and availability.

- Charging reservations and active sessions.

- Incidents, operational events, and telemetry.

- Assistant and AI Agent memory and searchable documentation

The approach uses the MongoDB document model to organize data around
application access patterns, while geospatial queries support
location-aware discovery, conditional updates help maintain accurate
availability, and change streams connect operational state changes with
downstream processing. 

AI agents work on the same data that the application uses and adapt to
who is asking. For drivers, they answer questions about past sessions.
For operators, they summarize and review incidents by combining
telemetry, incident history, and equipment manuals. 

Consolidating operational data into one flexible
platform allows your team to build connected charging applications that
adapt as networks, data requirements, and operational needs grow.

Reference Architectures
-----------------------

The solution brings driver experiences, charging operations, station
simulation, and operational data together through a unified app
architecture.

.. figure:: /includes/images/industry-solutions/connected-ev-charging2.2.svg
   :figwidth: 1200px
   :alt: EV charging demo architecture
   :lightbox:

   Figure 2. EV charging demo architecture

The Next.js app provides two primary experiences:

- **Driver App**: Used for station discovery and charging-session
  management.

- **Operations Control Center**: Used to monitor real-time charging
  activity and operational data.

The app communicates bidirectionally with the Charging Station
Management System (CSMS), built with Apollo GraphQL. The CSMS provides
the app contract for charging workflows and connects app actions with
charging-station operations. The app also integrates with location-based
services through OpenStreetMap to support station discovery and
location-aware experiences.

A Python FastAPI simulator represents charging-station activity and
generates session telemetry. The simulator communicates with the CSMS
through the `Open Charge Point Protocol
<https://openchargealliance.org/>`__ (OCPP) version 2.1. At startup, it
sends a boot notification to simulate a new online station. During
charging, the simulator tracks status changes and broadcasts telemetry
using transaction events. The CSMS stores these records in MongoDB so
the application and AI agents can access them immediately.

An AI agent queries this operational data layer directly to perform the following tasks:  

- Solve real-time user reports
- Process live station information
- Analyze telemetry logs
- Retrieve historical session context

The agent also answers complex questions for drivers and operators
instantly.

MongoDB provides the unified operational data platform across the
architecture. It integrates all data required for the end-to-end
charging experience—from driver and vehicle context to charging
infrastructure, session activity, operational events, and high-volume
telemetry.

As your solution evolves, MongoDB capabilities such as :ref:`geospatial
queries <geospatial-queries>`, :ref:`time series collections
<manual-timeseries-landing>`, :ref:`Atlas Search <fts-top-ref>`, and
:ref:`Online Archive <online-archive-overview>` support varied data and
access patterns.

Data Model Approach
-------------------

The data model follows the way EV charging applications actually work:
drivers need a complete view of a charging session, station searches
need location and availability together, while telemetry needs to be
handled as a high-volume stream. The MongoDB document model lets you
shape each collection around those specific access patterns.

The solution uses the following core collections:

- ``users`` and ``vehicles``: Store driver and vehicle information.

- ``chargingStations`` and ``chargingPoints``: Track station discovery
  and Electric Vehicle Supply Equipment (EVSE) state.

- ``chargingSessions``: Manage bookings, active sessions, and charging
  history.

- ``incidents``: Track operational issues.

- ``telemetry``: Store high-volume charging data.

- ``manualChunks``: Stores charging point documentation enriched with
  vector embeddings.

- ``agent_checkpoints``: Stores snapshots of each conversation's state,
  serving as the agent's memory.

- ``agent_checkpoint_writes``: Stores the intermediate steps the agent
  records for each checkpoint.

The document model makes the solution intuitive and easier to implement.

For example, the ``chargingSessions`` collection uses the Extended
Reference Pattern to keep session history data together. Alongside
references to the underlying vehicle and station, the session stores
small snapshots of the relevant details.

.. code-block:: JSON

   {
     "status": "COMPLETED",
     "stationSnapshot": {
       "name": "Downtown Mall Charging",
       "addressShort": "Main St 10, Zurich",
       "chargingPointLabel": "Bay 1"
     },
     "vehicleSnapshot": {
       "make": "BMW",
       "model": "i3"
     },
     "charging": {
       "energyDeliveredKwh": 52.4
     },
     "pricingSnapshot": {
       "currency": "EUR",
       "priceCentsPerKwh": 55
     },
     "cost": {
       "totalCents": 2882
     }
   }

When drivers view their session history, the app retrieves this
information from a single document without joining multiple collections.
The snapshots also preserve historical session context even if the
underlying station or vehicle data changes later.

The same principle simplifies station discovery. The
``chargingStations`` collection stores its location as :ref:`GeoJSON
<geospatial-indexes-store-geojson>`, enabling MongoDB geospatial queries
to find stations near a driver's location. It also maintains computed
availability counts and a bounded projection of charging-point
capabilities, so common map and search queries can be answered directly
from the station document.

.. code-block:: JSON

   {
     "name": "Downtown Mall Charging",
     "location": {
       "type": "Point",
       "coordinates": [8.5417, 47.3769]
     },
     "availability": {
       "availableNowPoints": 7
     },
     "chargingPoints": [
       {
         "connectors": [
           { "type": "CCS", "power": 150 },
           { "type": "TYPE2", "power": 22 }
         ]
       }
     ]
   }

Frequently changing operational state stays in the separate
``chargingPoints`` collection to avoid updating station documents
whenever a charging point's status changes. This separation also keeps
the model efficient as telemetry volume grows.

Telemetry has a different access pattern: it is high-volume, time-based,
and continuously growing. The solution keeps telemetry separate and uses
a :ref:`MongoDB time series collection <manual-timeseries-landing>` with
a :ref:`TTL index <index-feature-ttl>` to automatically enforce
retention policies. For longer-lived data, :ref:`MongoDB Online Archive
<online-archive-overview>` moves older data to lower-cost storage,
providing a native way to manage the data lifecycle without building
separate archival workflows.

.. code-block:: JSON

   {
     "timestamp": "2026-02-12T08:11:58Z",
     "meta": {
       "stationId": "65c8f2e2d2f4c3a9b3b9b001",
       "chargingPointId": "65c8f2e2d2f4c3a9b3b9b101",
       "stationCode": "station-001",
       "chargingPointCode": "cp_station-001_01"
     },
     "messageType": "SESSION_SAMPLE",
     "ok": true,
     "powerKw": 120,
     "energyKwhDelta": 0.4,
     "voltageV": 400,
     "currentA": 300,
     "temperatureC": 31.2
   }

The AI agent works on the same collections as the application, so its
answers reflect the live state of the network. Several additions make
the model AI-ready.

The ``manualChunks`` collection stores each manual section with its
heading, error codes, and a vector embedding in one document. A `MongoDB
Vector Search
<https://www.mongodb.com/products/platform/atlas-vector-search>`__
index filters on error codes and products. A MongoDB Search index on the
same collection matches exact codes and terms.

.. code-block:: JSON

   {
     "section": "7.3 Overtemperature protection",
     "heading": "Connector overheating",
     "codes": ["E-05"],
     "product": "ArcPort Home 22",
     "revision": 10,
     "text": "If the connector temperature exceeds…",
     "embeddingModel": "voyage-3.5",
     "embedding": [0.0213, -0.0187, …]
   }

When the AI agent reviews an incident, it writes its decision to the
incident document. The decision includes the likely cause, recommended
fix, disposition, confidence level, and the manual sections and tools
that the agent used. Operators see the full reasoning in the incident
view, and every decision stays auditable.

.. code-block:: JSON

   {
     "type": "USER_REPORT",
     "severity": "MEDIUM",
     "status": "OPEN",
     "stationId": "69a41eb930650a07a2823f77",
     "chargingPointId": "69a41eb930650a07a2823f79",
     "sessionId": "6adfbda1a82216749151a7fd",
     "detection": { "source": "USER" },
     "description": "Multiple tries to start charging",
     "createdAt": "2026-10-26T20:53:14.086Z",
     "resolution": {
       "resolvedAt": null,
       "review": {
         "reviewedAt": "2026-10-26T20:53:29.591Z",
         "summary": "User reported",
         "likelyCause": "Mechanical connector",
         "disposition": "MAINTENANCE_SCHEDULED",
         "scheduledFor": "2026-10-28T09:00:00.000Z",
         "nextStep": "Schedule maintenance",
         "confidence": "medium",
         "estimatedRepairTime": "1 day",
         "toolsUsed": [
           { "tool": "getSelectedChargerDetails" },
           { "tool": "summarizeStationIncidents" },
           { "tool": "skimTelemetry" },
           { "tool": "searchManuals" }
         ]
       }
     }
   }

The AI agent stores each conversation as checkpoints in MongoDB. A TTL
index removes inactive threads after seven days. Follow-up questions
keep their context without a separate memory service.

These patterns keep the implementation focused on the application's
actual workflows while enabling each data type to scale and evolve
independently. The result is a practical document model that reduces app
complexity without sacrificing flexibility.

Build the Solution
------------------

To run the solution locally, complete the following steps:

.. procedure::
   :style: normal

   .. step:: Set up the environment.

      Install Docker, clone the repository, and copy ``.env.example`` to
      ``.env`` to add your MongoDB Connection String.

   .. step:: Start the solution.

      Run ``make build`` to start the app, the CSMS backend, and the
      charging station simulator. The solution automatically seeds the
      database the first time you run it.

   .. step:: Explore the app.

      Open ``http://localhost:3000`` to test the driver journey: find a
      nearby station, filter charging points, make a reservation, start
      a session, and report an incident.

   .. step:: Explore operations.

      Switch to the Operations Control Center to view session activity,
      telemetry, utilization, incidents, and analytics as charging
      activity changes.

For the complete setup instructions, local development options,
environment variables, and additional commands, see the `GitHub
repository
<https://github.com/mongodb-industry-solutions/leafy-ev-charging>`__.

Key Learnings
-------------

- **Unify EV charging data and operations**: Consolidate driver
  experiences, charging infrastructure, operational data, and telemetry
  onto a single operational data platform to improve visibility and
  simplify architecture.

- **Simplify development and evolution**: Use the MongoDB flexible
  document model and schema patterns to build and adapt charging
  workflows as requirements change.

- **Build for availability and scale**: Combine real-time data,
  event-driven processing, and native MongoDB capabilities to support
  responsive charging experiences as infrastructure and data volumes
  grow.

- **Ground AI agents in live operational data**: The AI assistant
  queries MongoDB through tools instead of data copies and stores
  embeddings and conversation memory in the same platform. Answers
  reflect the current state of the network without a separate vector
  database or synchronization pipeline.
